# 重复操作能不能交给脚本？——Testlab Automation、MATLAB 与批处理接口

> 同一份工作反复做了几十遍，每一遍都是同样的点击、同样的对话框、同样的导出——人变成了流程里最慢、也最容易走神的一环。本文回答一个工程部门的现实问题：哪些重复操作该交给软件、交给哪一层软件。从 Process Designer 的流程文件、Workflow Automation 的整场批处理，到 Automation 接口让 MATLAB、Excel VBA、Python 这些外部程序直接“当司机”指挥 Testlab 干活，一层层往上走，每层给出判断标准与工时账：50 个 run 的处理从手工 10 小时压到脚本 5 分钟，4 因素 3 水平的 81 个 DOE 工况从两个白天压到一夜。

::: tip 30 秒速览
- **一句话**：每天重复几十遍的点击，到底哪些能交给软件、交给哪一层？
- **类比**：像打车——你（外部程序）说出目的地，司机（Testlab）熟悉路并开车；流程文件是定线公交，批处理是包车，脚本驱动是随叫随到的专车。
- **关键数字**：50 个 run 的同样处理，手工 10 小时、脚本 5 分钟；81 个 DOE 工况手工要做两个白天，脚本一夜跑完。
- **结论**：同样的操作重复 3 遍就该存成流程文件；要吃整场数据用批处理；要按参数表逐点扫、要读数反哺下一步，才轮到脚本驱动——层级选对，人只做判断题。
:::

## 一、先看一个凌晨两点的屏幕

一个试验部门都能对号入座的场景：某车型耐久路面试验做完，数据回来 50 个 run。处理流程早就定死了——读入时历、按工况切段、算自谱、提 2 阶与 4 阶、按 run 平均、导出曲线。分析员熟练地打开第一个 run，从导航器拖数据、点开处理页、设段、跑流程、右键导出、另存、命名 Run01 的 2 阶结果表。一个 run 十二分钟，全程约四十次点击，没有一次需要动脑。到第三个，他开始听着播客点鼠标；到第十个，两次把 Run13 的结果存成了 Run31。凌晨两点，第 41 个 run，屏幕上的曲线看起来都长得一样，他没能发现自己把一个方向选错了——这种错不会有任何报错，直到评审会上才被人眼抓出来。

值得停下来想一件事：**这一晚上没有任何一步是“分析”，全部是“搬运”**。判断（流程怎么定、参数取多少）早在第一周就做完了，剩下的四十多遍执行，人只是充当了一根会走神的连接线。把执行还给软件，人只做第一遍的判断——这就是自动化要解决的全部问题，也是“重复操作能不能交给脚本”这个问题的标准答案：**能，但要先选对交给哪一层**。

Testlab 生态里其实备好了一整排工具：Process Designer 把流程存成文件，Workflow Automation 拿着流程文件吃整场数据，Automation 接口干脆让外部程序当司机。多数团队卡住的原因不是工具不够，而是分不清这几层的边界——要么拿着脚本干批处理的活（写两周代码解决一个菜单命令的事），要么用手工重复硬扛本该脚本干的参数扫描（81 个工况做两个白天）。

## 二、先分清三层：定线公交、包车与专车

把 Testlab 的自动化能力想成**城市里的三种车**，这个比方会贯穿全文：

- **流程文件（Process Designer 的 *.process）是定线公交**：路线（处理步骤）画一次，站名（参数）写在站牌上，数据上车坐到底。它最便宜、最该先用——但路线固定，数据得自己走到站台。怎么搭这条“路线”、把参数抽成变量表，见《[流程搭好了，为什么换批数据就失效？](neo-process-designer-variables.html)》。
- **批处理（Workflow Automation）是包车**：还是那条路线，但一辆车把整场试验几十个 run 全部拉走，司机（软件）按名单逐个跑，天亮交一整册结果。
- **Automation 接口是随叫随到的专车**：你（MATLAB、Excel VBA、Python、C#）坐在后座说目的地，Testlab 这个“老司机”负责实际开车——它认路（算法与数据都在它那里），你负责决定去哪、下一站去哪。

第三层是本文的主角，也是最多人误解的一层：**脚本不是把 Testlab 的功能“抄一遍”，而是指挥 Testlab 自己干**。这个差别决定了它为什么值得单独一层，先看它的结构。

### 2.1 专车的结构：COM 接口与对象树

Automation 接口的本名是 **COM 自动化接口（Automation Server）**：Testlab 启动后对外注册一个**应用程序对象（Application Object）**作为根，往下挂着一整棵对象树——窗口框架（Frame）、项目（Project）、数据浏览、显示页（Display）、游标（Cursor）等。外部程序通过这棵树读写属性、调用方法，就像人用鼠标在界面里逐层点开一样，只不过换成了程序对程序。

![Automation 接口的分层结构：外部程序—COM 接口—Testlab 对象树](/images/testlab-automation-matlab-api/fig2-com-architecture.png)

*（图源：网络 侵删）*

这张结构图里藏着三个工程要点。**第一，数据不出系统**：脚本调用的是 Testlab 里现成的算法与项目数据，算完的结果仍然留在原项目里，不存在“导出—外部处理—再导回”的三次搬运。**第二，能力与界面同源**：菜单里能做的（跑一段处理、读一个游标值、打印一页报告），对象树上就有对应的方法——界面是给人看的皮，接口是给程序用的骨。**第三，树形导航有代价**：每一步都拿到对象再走到下一个对象，路径越长越脆，这正是后面“常见坑”一节的伏笔。

```text
外部程序（MATLAB / VBA / Python / C#）
   |  方法调用 / 属性读写
   v
Application（根对象：启动、打开项目、遍历窗口）
   |-- Frame -- Display（显示页：加曲线、设坐标）
   |             |-- Cursor（游标：读峰值频率、峰值幅值）
   |-- Project -- Data Explorer（数据导航：按 run/通道检索）
   |-- 其他对象（打印、导出、处理作业等）
```

### 2.2 专车比方的第二条纪律：司机只认路，不替你决定去哪

专车比方还有第二层：**司机再熟路，也不会替你选目的地**。Automation 接口同样只提供“手”，不提供“脑”——扫哪个参数、读到什么值算合格、下一步往哪走，全是外部程序里的逻辑。这就是它与流程文件最本质的分工：流程文件把“判断的结果”固化（这条路线跑到底），脚本把“判断的规则”外置（你的 MATLAB 或 Python 程序边跑边判断）。后文第四节 DOE 扫描的例子里会看到，这条分工线正好把“逐点守护”压缩到每点半分钟。
## 三、第一笔账：什么值得脚本化

不是所有重复都值得交给脚本。判断标准只有一条：**执行次数 × 每次工时 × 出错代价，要大于搭自动化的成本**。这个公式回答的问题是“这件事交给软件到底省不省”：

$$T_{\text{\u624b\u5de5}}(N) = N \cdot t_m \, , \qquad T_{\text{\u811a\u672c}}(N) = c_s + N \cdot t_w$$

其中 N 是重复次数，$t_m$ 是手工每遍的分钟数，$c_s$ 是写脚本或搭流程的一次性成本（摊销），$t_w$ 是脚本跑每遍时人还必须盯着的守护分钟数。两条线一画，交点就是盈亏平衡点——低于它，手工反而快。

![手工与脚本的总工时随 run 数的变化：交点即盈亏平衡](/images/testlab-automation-matlab-api/fig3-cost-model.png)

*（图源：网络 侵删）*

代入开头那晚的数字：一个 run 十二分钟、约四十次点击；流程若已存成文件，人只剩“换数据、点运行”的守护动作，折合每 run 约六秒；写脚本的两小时成本按整场摊销约两分钟。三笔数一并排，结论就出来了。

<details>
<summary>数值实验：手工 vs 脚本的工时账（10 行）</summary>

```python
import numpy as np

runs = np.array([1, 5, 13, 50, 100])
per_manual = 12.0          # min/run：约 40 次点击 + 导出粘贴
fixed_script, per_script = 2.0, 0.06   # 写脚本摊销 2 min，每 run 6 s 守护时间
T_man = runs * per_manual
T_scr = fixed_script + runs * per_script
n_breakeven = fixed_script / (per_manual - per_script)
for r, a, b in zip(runs, T_man, T_scr):
    print(f"{r:3d} run: 手工 {a:6.1f} min | 脚本 {b:6.2f} min | 差 {a/b:6.1f} 倍")
print(f"盈亏平衡点 N* = {n_breakeven:.1f} 个 run")
print(f"50 run 一场：手工 {T_man[3]/60:.1f} h，脚本 {T_scr[3]:.1f} min（含摊销）")
```

运行结果（本机实跑）：

```text
  1 run: 手工   12.0 min | 脚本   2.06 min | 差    5.8 倍
  5 run: 手工   60.0 min | 脚本   2.30 min | 差   26.1 倍
 13 run: 手工  156.0 min | 脚本   2.78 min | 差   56.1 倍
 50 run: 手工  600.0 min | 脚本   5.00 min | 差  120.0 倍
100 run: 手工 1200.0 min | 脚本   8.00 min | 差  150.0 倍
盈亏平衡点 N* = 0.2 个 run
50 run 一场：手工 10.0 h，脚本 5.0 min（含摊销）
```

注意这笔账的关键在两个小数：$t_m=12$ 分钟里几乎没有判断，而 $t_w=0.06$ 分钟只覆盖“脚本换下一个输入”的机器时间——**人从执行者降级为第一遍的判断者**，这正是自动化该有的样子。

</details>

但工时只是显性的一半。隐性的一半是**错误率**：四十次无脑点击做五十遍，等于两千次不出错的机会窗口；凌晨两点把 Run13 存成 Run31、方向选错却不报错，都是这条窗口里的真实事故。脚本的价值不只是快，而是**第 50 遍和第 1 遍一字不差**——执行一致性本身就是质量。

## 四、第二笔账：什么时候必须上脚本

上面那笔账里，流程文件和批处理就已经能把 50 个 run 压到 5 分钟——看起来脚本层多此一举？不。有三类活，只有外部程序驱动干得了，因为它们都需要**“读结果、再决定下一步”**的闭环。

**第一类：DOE 参数扫描。** 悬挂 K&C 台架上的参数试验：胎压三档、载荷三档、阻尼三档、车速三档，4 因素 3 水平全因子 81 个工况。手工的做法是拿张表逐行改参数、采一段、出一版结果——每点十五分钟，两个白天。脚本驱动的做法是把这张参数表放在外部程序（MATLAB 或 Excel）里，逐行读出、通过接口写进 Testlab 对应字段、触发采集与处理、把结果记录回表的同一行——每点人只守护半分钟。

<details>
<summary>数值实验：81 个 DOE 工况的两种做法（9 行）</summary>

```python
import numpy as np

factors = {'胎压(kPa)': [220, 240, 260], '载荷(kg)': [1600, 1800, 2000],
           '阻尼档': [1, 2, 3], '速度(km/h)': [50, 80, 110]}
n = 1
for lv in factors.values():
    n *= len(lv)
print(f"因素数 4、各 3 水平：全因子组合数 = 3^4 = {n} 个工况")
per_cfg = 15.0   # min：改参数 + 采一段 + 出一版结果
print(f"手工逐点：{n} x {per_cfg:.0f} min = {n*per_cfg/60:.1f} h")
print(f"脚本驱动：改参-采集-处理-记录每点守护 0.5 min = {n*0.5:.1f} min，一夜跑完")
```

运行结果（本机实跑）：

```text
因素数 4、各 3 水平：全因子组合数 = 3^4 = 81 个工况
手工逐点：81 x 15 min = 20.2 h
脚本驱动：改参-采集-处理-记录每点守护 0.5 min = 40.5 min，一夜跑完
```

</details>

**第二类：结果反哺下一步。** 台架试验做到“每个转速点找共振最大”这类自适应流程：脚本在显示页上放一个游标对象，读出当前转速下峰值频率与幅值，判断是否超过门槛，再决定下一个转速点扫多细。流程文件做不到这件事，因为它在跑之前就把所有步骤定死了；游标读数每跑一遍都在变，必须有“脑”在循环外边看边决定。

**第三类：跨软件拼装。** Testlab 里没有的算法（某个自定义的声品质指标、某个内部开发的损伤模型），在 MATLAB 里写好；数据从 Testlab 项目里按通道读出、送进 MATLAB 算、结果再写回项目的数据集——全程不落中间文件。往返搬运的数据量级值得心里有数：40 通道、20480 Hz、120 秒的一段时历是每通道 2.5 M 样本，二进制单精度矩阵约 0.37 GiB——靠人工抄表（每通道抄峰值与 RMS 两个数，约 640 字符）等于把信息量压到约六十万分之一，而矩阵往返几秒钟就完。
<details>
<summary>数值实验：一段时历往返搬运的字节数（7 行）</summary>

```python
import numpy as np
fs, T, nch = 20480, 120, 40
samples = fs * T
bytes_f64 = samples * nch * 8
bytes_f32 = samples * nch * 4
print(f"{nch} 通道 x {fs} Hz x {T} s = {samples/1e6:.1f} M 样本/通道")
print(f"二进制矩阵 f64: {bytes_f64/2**30:.2f} GiB | f32: {bytes_f32/2**30:.2f} GiB")
manual = nch * 2 * 8   # 每通道峰值+RMS，一个数按 8 字符计
print(f"人工抄表（每通道峰值+RMS）: {manual} 字符——信息量差 {bytes_f32/manual:.3g} 倍")
```

运行结果（本机实跑）：

```text
40 通道 x 20480 Hz x 120 s = 2.5 M 样本/通道
二进制矩阵 f64: 0.73 GiB | f32: 0.37 GiB
人工抄表（每通道峰值+RMS）: 640 字符——信息量差 6.14e+05 倍
```

</details>

顺带把 MATLAB 的位置说清：公开技术资料里，Testlab 与 MATLAB 的互通有多条路——Automation 接口从 MATLAB 建立连接遥控；MATLAB 里算好的矩阵写回 Testlab 项目；以及 Testlab 处理流程中嵌入 MATLAB 脚本步骤。选哪条，取决于“脑”放在哪边：脑在 MATLAB（优化算法、自定义模型）就接口遥控，脑在流程里（偶尔调一个现成函数）就嵌入步骤。

## 五、五层工具对号入座

把前面几层拉成一张递进表，就是“重复操作交给谁”的完整答案：

![从手工到脚本驱动的递进选型表：按需求特征对号入座](/images/testlab-automation-matlab-api/fig4-decision.png)

*（图源：网络 侵删）*

![五种自动化方式的阶梯：越往上越自由，也越需要编程投入](/images/testlab-automation-matlab-api/fig1-ladder.png)

*（图源：网络 侵删）*

四条判断从上往下问：

1. **同一操作重复 3 遍以上、点击顺序一样？** 先存流程文件——成本最低、无编程，且立刻获得 Checks 质检与边采边算的 Data Streaming（采集端的入口见《[传感器都接对了，第一条时历为什么还是作废？](neo-time-data-acquisition.html)》）。
2. **要吃整场试验几十上百个 run？** 上 Workflow Automation 批处理，让流程文件当包车整夜跑；配合 Q 查询还能把结果自动写进报告（见《[结果算完了，报告为什么还要手工贴图？](neo-reporting-batch-powerpoint.html)》）。
3. **参数要按 DOE 表逐点扫、或要读游标/读结果决定下一步？** 这才轮到脚本驱动——用 Automation 接口，MATLAB、VBA、Python 坐后座指挥。
4. **Testlab 里没有的算法？** 数据导出矩阵、外部算完写回，或处理流程里嵌入脚本步骤。

四条都不满足的活，手工点菜单反而最快——**自动化的目的不是消灭点击，是消灭不值得人做的点击**。

## 六、常见坑：专车也会堵车

::: warning 常见坑
- **版本与许可**：Automation 接口与各自动化能力随版本演进，具体可用的对象、方法与所需许可以所用版本的相关技术文档为准——脚本大范围铺开前，先在目标机器上小规模验证。
- **界面改版，对象树跟着变**：外部程序沿对象树导航，版本升级后对象名与路径可能变化；升级前把关键脚本回归跑一遍，别等量产数据回来才发现断在第一行。
- **守护时间不是零**：脚本跑批时人仍要盯日志与异常分支（磁盘满、数据缺失、许可掉线），把守护时间按 0 计的排产必然翻车。
- **能用流程文件别用脚本**：脚本最大的成本在维护——写它的人调走之后，一段三百行的 VBA 就是全组最脆的资产。层级选低的，够用就走。
- **异常要写进脚本**：磁盘满、通道缺失、数据越界这些分支，人肉跑流程时靠眼睛兜底，脚本化后必须在代码里显式处理，否则失败静默、结果带病流向下游。
:::

## 七、从“会跑”到“可托付”

把这套阶梯放回一个试验部门的日常：新员工入职先学流程文件（一周搭出第一份流程，Checks 挂上）；组里成型的试验类型交给批处理（一夜之间 50 个 run 变一册结果，早晨只看例外清单）；真正需要研究的课题——DOE 扫描、自适应寻优、跨软件模型——才投入脚本开发，而且脚本的第一版往往就是“把参数表读进来、逐行驱动、把结果记回去”三十行以内的事。三层各就各位之后，人会发现自己剩下的工作恰好是机器做不了的那部分：定流程、定参数、判读例外、做决定。

打车比方收尾：**定线公交（流程文件）解决天天走的路，包车（批处理）解决一整批的货，专车（脚本驱动）解决“下一站去哪现在才知道”的活**。三种车都在车队里，别用专车拉公交的客，也别用两条腿跑专车的活。

## 一句话记住

> 重复三遍存流程，整场数据交批处理，参数扫描与结果反哺才上脚本——层级选低不选高，人只做判断题，执行一字不差地交给软件。
