# 三年的测试数据都在，为什么还是训不出一个能用的模型？——测试数据的七项 AI 就绪条件

> 试验部门最有底气的家底，就是积累了几年的测试数据——车型换代、载荷谱、路噪、模态，一柜子硬盘。可当数据科学家真要把它们喂给模型，第一周就卡住了：文件名对不上工况、通道设置查无实据、一半结果没人确认过对错。本文回答这个越来越常见的问题：为什么"能训练"和"适合 AI"是两件事。用一笔标注工时账（200 个 run 从 20 小时压到 3 小时）、一张工况覆盖表（108 个组合缺 12 个）和一次故障样本混入实验（4% 的坏样本把模型误差抬高 12%），逐项过一遍测试数据在喂给模型之前必须满足的七项就绪条件，以及每一项在采集—处理—管理链条上对应的落地位置。

::: tip 30 秒速览
- **一句话**：硬盘塞满测试数据，为什么模型还是"吃不饱"？
- **类比**：像电商仓库发货——货没破损（质量）、盖过质检章（有效）、贴了面单（可追溯）、品类齐（完备）、分量够（数量）、货架找得到（可达）、上得了传送带（连通），七样缺一，自动分拣线就停摆。
- **关键数字**：200 个 run 的标注，全部留给现场要填 20 小时；模板预先填好 85%，现场只剩 3 小时。
- **结论**：模型训练只要几分钟，数据准备要几周——七项条件是验收清单不是口号，且要从采集端开始把关，而不是从训练开始补救。
:::

## 一、AI 项目第一周，卡住的不是算法

一个正在各大试验部门真实上演的场景：团队决定用机器学习预测路噪 KPI，数据科学家入职第一周信心满满——"三年的数据都在，先拉出来训一版"。然后他发现：模型代码 5 分钟就跑通了，**找数据用了两周**。有的结果在退役的旧工作站上，有的在离职同事的移动硬盘里；找回来的文件里，一半说不清是哪个配置、哪种工况、哪个软件版本算出来的；其中还有几段通道灵敏度录错的数据——当年发现时重新测了，坏的那份却没删，和好的混在同一个文件夹里。

把上面这个场景拆开看，卡住他的每一件事都有名字：找不到文件，是**可达性**问题；说不清配置与工况，是**可追溯**问题；坏数据和好数据混放，是**有效性**问题；灵敏度录错的段落在当年就该被监视页拦下，是**质量**问题。也就是说，AI 项目第一周撞的墙，没有一块是"算法不行"，全是数据在入库那一刻欠下的账。业内把这些账整理成一张验收单：数据要喂给模型，先过**七项就绪条件**——质量、有效性、可追溯、完备性、数量、可达性、连通性。这七个词后面逐项展开，这里先把最重要的一条记下：**七项里的大多数，只能在数据产生的那一刻满足，事后补，要么补不上、要么按十倍的工时补**。

值得先把一笔账算清楚：这类项目的瓶颈从来不在训练。训练在 GPU 上以分钟计，而**数据准备**以周计。准备工时里最大的一块，是把"存下来的文件"变成"说得清楚的数据"，也就是给数据补标注。这个公式回答的问题是"一场试验的标注到底要花多少现场工时"：

$$T_{\text{标注}} = N \cdot n_f \cdot t_f \cdot (1-\eta)$$


其中 $N$ 是 run 数，$n_f$ 是每个 run 要填的标注字段数，$t_f$ 是手填一个字段的分钟数。那个希腊字母 $\eta$ 是**在试验开始前就能预先填好的比例**——它就是全部杠杆所在：车型、测点布置、通道表、软件设置这些字段，在试验开始前就完全确定；真正要到现场才填的只有天气、温度这类少数几项。把 $\eta$ 从 0 提到 0.85，200 个 run 的标注工时从 20 小时缩到 3 小时——这笔账第四节会用 numpy 复算。

而标注只是七项条件中的一项。先看全貌。

## 二、七问清单：一张仓库验收单

::: info 核心概念
**AI 就绪数据（AI-ready data）**：除了工程上正确之外，还满足机器学习工作流要求的测试数据——可信、已验证、可追溯、覆盖完整、数量充足、可检索、可自动流转。数据"正确"只保证它能回答当年的工程问题；"就绪"才保证它能被模型安全地学习。
:::

把测试数据想成一座**电商仓库**，这个比方贯穿全文：模型是仓库尽头的自动分拣线，分拣线越先进，对到货的要求越苛刻。进货验收单上七个问题，一个都答不上来，分拣线就停一格：

| # | 问题 | 仓库版 | 数据版 |
|---|---|---|---|
| 1 | 质量 Quality | 货本身没破损 | 采集硬件可信，故障当场暴露 |
| 2 | 有效性 Validity | 盖过质检章 | 结果被确认正确，不只是"被保存" |
| 3 | 可追溯 Traceability | 每件贴面单 | 配置、条件、状态可查，不用问人 |
| 4 | 完备性 Completeness | 菜单上的品类都有 | 工况覆盖含边角案例 |
| 5 | 数量 Quantity | 单品分量够一箱 | 样本够训练，不够能补 |
| 6 | 可达性 Accessibility | 货在货架上、有编号 | 按属性检索，不发邮件找人 |
| 7 | 连通性 Connectivity | 上得了传送带 | 验证—提取—发布能自动化 |

![AI 就绪数据工作流：从采集、标注、处理到交付的完整链条](/images/ai-ready-test-data-seven-pillars/fig1.png)

*（图源：网络 侵删）*

七项不是并列的口号，而是一条**从采集端倒推回数据端**的流水线：第 1 项在传感器与采集硬件端把关，第 2、3 项在处理与标注环节落地，第 4、5 项是试验设计问题，第 6、7 项靠数据管理与自动化。下面按这条链逐项过账。

## 三、质量与有效性：货没破损，还要盖质检章

**质量（Quality）是第 1 项，也是唯一无法事后补救的一项。** 关键认知只有一句话：AI 模型分不清"物理规律"和"传感器故障"——它会把两者一起学进去。松动的加速度计、贴顶削波的通道、整场读数偏低的麦克风，只要混进训练集，就成了"规律"的一部分。

这和人工读数完全不同：工程师看谱会本能地跳过一段明显异常的数据，模型没有这个本能。用一次最小实验定量感受一下——结论先摆在这段代码跑出来的数里：训练集里混入 4% 来自故障通道（读数整体掉到 0.6 倍）的样本，一次线性拟合的测试误差从 0.079 抬到 0.088，大 12%；更麻烦的是斜率从 1.999 偏到 1.973——**物理规律本身被改写了**，而用这份模型做设计决策的人毫不知情。

<details>
<summary>数值实验：4% 故障样本混入训练集，模型误差与斜率被带偏多少（24 行）</summary>

```python
import numpy as np

# 账：质量——传感器故障混进训练集，模型把故障当物理规律学走
rng = np.random.default_rng(3)
n_train, n_test = 3000, 500
fault_rate = 0.04                       # 训练集里 4% 的样本来自故障通道

def make_data(n, rng, fault=False):
    x = rng.uniform(0.5, 2.5, n)        # 转速工况
    y = 2.0 * x + 0.1 * rng.standard_normal(n)
    if fault:                           # 松动通道：响应整体掉到 0.6 倍
        y = y * 0.6
    return x, y

x_tr, y_tr = make_data(n_train, rng)
i_fault = rng.random(n_train) < fault_rate
x_f, y_f = make_data(int(i_fault.sum()), rng, fault=True)
x_tr[i_fault], y_tr[i_fault] = x_f, y_f
x_te, y_te = make_data(n_test, rng)

# 干净训练 vs 带故障训练（一次线性拟合当"模型"）
A_clean = np.polyfit(x_tr[~i_fault], y_tr[~i_fault], 1)
A_dirty = np.polyfit(x_tr, y_tr, 1)
err_clean = np.abs(np.polyval(A_clean, x_te) - y_te).mean()
err_dirty = np.abs(np.polyval(A_dirty, x_te) - y_te).mean()
print(f"训练集 {n_train} 样本含 {int(i_fault.sum())} 个故障样本（{fault_rate:.0%}）")
print(f"干净模型测试误差 {err_clean:.3f}，带故障训练 {err_dirty:.3f}（大 {(err_dirty/err_clean-1)*100:.0f}%）")
# 斜率被带偏多少——物理规律本身被改写
print(f"斜率：干净 {A_clean[0]:.3f}（真值 2.000），带故障 {A_dirty[0]:.3f}")
```

</details>

所以质量的把关必须发生在**采集现场**：SCADAS 这类采集硬件在测量端保住信号完整性，并把过载、连接、校准信息与数据存在一起——而不是记在另一本可能丢失的纸质日志里。量程怎么选、贴顶怎么当场发现，见《[传感器都接对了，第一条时历为什么还是作废？](neo-time-data-acquisition.html)》。

**有效性（Validity）是第 2 项，回答"这些结果是确认过的，还是只是恰好被存下来的文件"**。仓库的比方：质量保证货没破损，有效性是质检章——有人**看过并确认过**。手工逐条核对几千个结果不现实，这条路要走自动化校验：Testlab Neo 的 Process Designer 里可以把"时历检查、块结果对目标线、单值对门槛"做成流程里的 Checks 步骤，每次运行自动判、超限自动标——怎么把这些判据做成变量化、可复用的流程，见《[流程搭好了，为什么换批数据就失效？](neo-process-designer-variables.html)》。有效性检查做得越靠前，训练集里"带病样本"的比例就越低——第三节那 4% 的实验就是它的反面教材。

## 四、可追溯：每件货都要有面单

**可追溯（Traceability）是第 3 项**：拿到任意一个结果文件，不问当年做试验的工程师，就能说清它测的是什么配置、什么条件、什么状态。仓库的比方：面单。一千件没有面单的货堆在仓库里，分拣线再快也发不出去——因为不知道每件该去哪。

落地手段是**标注（Annotation）与描述性数据模型（Descriptive Data Model）**：用模板编辑器设计一套符合 ASAM 规范的属性模型（车型、动力形式、测点布置、工况、环境……），在采集前、采集中、采集后三个时机填写。第一节公式里的那个比例 $\eta$ 在这里兑现：车型、配置、通道表、软件设置在试验开始前就完全确定，公开技术资料给出的经验值是 80% 到 90% 的标注可以在试验开始前填好，真正留给现场的只有天气这类少数字段。这笔账展开就是一段 numpy——结论先摆在这段代码跑出来的数里：200 个 run、每 run 12 个字段、每字段 30 秒，现场全填 20 小时；预填 85% 后只剩 3 小时，省下的 17 小时正好是"现场来不及填、事后凭记忆补、补错混进训练集"这三类事故的总预算。

<details>
<summary>数值实验：标注工时账——预填比例把现场工时压掉多少（10 行）</summary>

```python
import numpy as np

# 账 1：标注工时——全部留给现场 vs 模板预填 85%
N = np.array([200, 400])          # 会话纳入的 run 数
n_fields, t_field = 12, 30.0      # 每 run 12 个标注字段，每字段手填 30 s
eta = 0.85                        # 模板预填比例（80~90% 的保守值）
T_manual = N * n_fields * t_field / 3600.0
T_spot   = N * (1 - eta) * n_fields * t_field / 3600.0
for n, tm, ts in zip(N, T_manual, T_spot):
    print(f"{n} run：现场全填 {tm:.1f} h，预填 85% 后只剩 {ts:.1f} h，省 {tm-ts:.1f} h")
```

</details>

面单的另一个价值在**标签质量**：预测模型的标签就是标注字段——"这个 run 是 C 级混动、西班牙试车场、粗糙路面"，标签错一格，模型学到的是错误的对应，而且当年没人发现。这也是为什么标注要在试验现场顺手完成，而不是三个月后对着文件夹猜。

## 五、完备与数量：菜单上有的，仓库里都得有

**完备性（Completeness）是第 4 项**：模型的预测范围不会超过训练数据的覆盖范围。仓库的比方：菜单上有的菜，仓库里都得有原料——哪怕那道菜一年只点一次。工程上最容易漏的恰恰是**边角工况**：极低温、满载爬坡、高速单测挡位……试验大纲偏爱常用工况，历史数据因此天然偏科。

偏科到什么程度，算一遍就知道。这个公式回答的问题是"如果每个特征都取离散档位，全部工况组合一共有多少格"：

$$N_{\text{all}} = \prod_{i=1}^{k} n_i$$

五个特征（路面 3 档、车速 3 档、温度 3 档、载荷 2 档、挡位 2 档）共 $3 \times 3 \times 3 \times 2 \times 2 = 108$ 格。按工程习惯的偏好抽样模拟 1200 个历史 run——结论先摆在这段代码跑出来的数里：只覆盖 96 格、缺 12 格（11%）；更值得警惕的是已覆盖的格子里，**37 格样本数不足 5 个**——模型在这些格子上等于在猜，而且不会提醒你它在猜。

<details>
<summary>数值实验：1200 个历史 run 覆盖 108 个工况组合中的多少格（22 行）</summary>

```python
import numpy as np

# 账 3：完备性——历史试验覆盖 vs 模型要预测的工况
grids = [3, 3, 3, 2, 2]                      # 路面 3 档 x 车速 3 档 x 温度 3 档 x 载荷 2 档 x 挡位 2 档
N_all = int(np.prod(grids))
rng = np.random.default_rng(11)

# 工程习惯：试验大纲偏爱常用工况——路面/温度/载荷的中间档、高速挡位极少单测
p_road  = np.array([0.45, 0.35, 0.20])       # 粗糙/中等/光滑路面
p_speed = np.array([0.30, 0.45, 0.25])       # 低/中/高速
p_temp  = np.array([0.15, 0.70, 0.15])       # 低温/常温/高温
p_load  = np.array([0.30, 0.70])             # 空载/满载
p_gear  = np.array([0.85, 0.15])             # 中间挡/最高挡
probs = [p_road, p_speed, p_temp, p_load, p_gear]

covered = set()
N_runs = 1200
for _ in range(N_runs):
    combo = tuple(int(rng.choice(g, p=p)) for g, p in zip(grids, probs))
    covered.add(combo)
missing = N_all - len(covered)
print(f"五个特征的全工况组合共 {N_all} 个")
print(f"{N_runs} 个历史 run 实际覆盖 {len(covered)} 个，缺 {missing} 个（{missing/N_all:.0%}）")

# 其中最稀疏的格子有多稀
from collections import Counter
cnt = Counter()
for _ in range(N_runs):
    combo = tuple(int(rng.choice(g, p=p)) for g, p in zip(grids, probs))
    cnt[combo] += 1
vals = np.array(sorted(cnt.values()))
print(f"已覆盖格子的样本数：最少 {vals.min()}、中位 {int(np.median(vals))}、最多 {vals.max()}")
sparse = sum(1 for v in vals if v < 5)
print(f"样本数不足 5 个的格子 {sparse} 个——模型在这些格子上等于在猜")
```

</details>

**数量（Quantity）是第 5 项**，与完备性是一对：完备管"每格都要有"，数量管"每格要够"。矛盾在于工程现实——样车越来越少、试验越砍越少，而模型胃口越来越大。补数的一条可信路径是**用仿真扩充实测**：基于部件的传递路径分析（C-TPA）与虚拟样机装配（Virtual Prototype Assembly）把实测部件特性组装成虚拟整车工况，生成的数据带物理约束、可与实测交叉验证——比"纯靠实测凑数"省钱，比"拍脑袋造数"可信。仓库的比方：旺季原料不够，中央厨房按同一配方预制半成品，而不是往货里掺水。

## 六、可达与连通：上得了传送带的才是产能

**可达性（Accessibility）是第 6 项**：数据找得到吗？仓库的比方：货在货架上、有编号，而不是堆在后院没人知道哪个箱子是哪个。工程版的"找不到"很具体：数据科学家要 95 个符合条件的 run，只能发邮件、追着试验工程师一个一个要文件。这笔账一算就疼——这个公式回答的问题是"按文件逐个人工沟通要多久"：

$$T_{\text{人工}} = N_{\text{命中}} \times t_{\text{件}}$$

1200 个 run 里命中 95 个（7.9%），每件人工沟通 5 分钟，就是 7.9 小时——而且下周换个筛选条件再来一遍。解法是把数据放进**集中部署的数据管理库**（如 Testlab Data Management，底层为 ASAM-ODS 数据库），按**属性**而不是文件名检索："C 级混动、西班牙试车场"一查即中，分钟级。

<summary>数值实验：属性检索 vs 逐个邮件——命中 95 个文件的工时差（12 行）</summary>

```python
import numpy as np

# 账 2：检索命中——按属性查 vs 挨个发邮件
rng = np.random.default_rng(7)
N_all = 1200                      # 三年积累的 run 总数
seg  = rng.choice(["C级混动", "C级燃油", "B级混动", "SUV混动"], N_all, p=[.3, .3, .2, .2])
site = rng.choice(["西班牙试车场", "本土试验场", "台架"], N_all, p=[.25, .6, .15])
mask = np.logical_and(seg == "C级混动", site == "西班牙试车场")
n_hit = int(mask.sum())
t_email = n_hit * 5.0 / 60.0      # 每个命中文件人工沟通 5 min
print(f"1200 run 中命中 {n_hit} 个（{n_hit/N_all:.1%}）：逐个邮件要 {t_email:.1f} h，属性查询约 2 min")
```

</details>

**连通性（Connectivity）是第 7 项，也是把前六项串起来的传送带**：验证、KPI 提取、标注、发布、检索这串动作，能不能不靠手工？Testlab Workflow Automation（TWA）可以对着数据管理库定义查询——"找出所有 C 级混动、西班牙试车场的实测"——然后自动取数、按流程重算、导出到 AI 训练平台。仓库的比方到这就闭环了：前六项保证每件货合格、有面单、在架上；传送带保证它们能**成批、无人值守地**流到分拣线。

## 七、把七项拼成一条流水线

七项条件单独看都不难，难的是**在一条链上同时成立**：

![完整的 AI 就绪数据工作流：采集、标注、处理、验证到交付一体的链路](/images/ai-ready-test-data-seven-pillars/fig6.png)

*（图源：网络 侵删）*

回看这张链路图，七项各就各位：质量在采集硬件端（过载/校准信息随数据走）；有效性与可追溯在处理与标注环节（Checks 自动校验、描述性数据模型预填八到九成）；完备性靠排程化的试验大纲强制执行；数量不够用 C-TPA/虚拟样机装配补；可达性靠数据管理库按属性检索；连通性靠 TWA 把整条链自动串起来。

给准备立项的团队一张行动清单，按投入产出排序：

1. **先摸底再立项**：拿第二节的七问清单对存量数据打分，答"否"超过一项，先补数据链路再谈模型。
2. **从下一场试验开始按 AI 就绪执行**：标注模板先建（预填比例提到 0.85）、Checks 先挂、排程先排——历史数据救不回来，新数据从第一天就是资产。
3. **故障数据当场标记**：质量是唯一不能事后补救的一项，采集现场的监视页就是最后一道防线。
4. **补数走仿真路线**：C-TPA/虚拟样机装配扩充，而不是降低验收标准。
5. **把检索和导出自动化**：凡是"发邮件要文件"的环节，都是模型上线后的瓶颈。

::: warning 常见坑
- **"数据都在"的错觉**：文件在不等于数据可达。硬盘上的文件没有属性检索，等于仓库堆在后院的纸箱。
- **标签靠回忆补**：试验三个月后凭记忆补标注，错误标签混进训练集比缺数据更糟——模型会自信地学错。
- **验证只对峰值**：有效性检查只看最大值会漏掉整场偏低的通道；块结果对目标线、单值对门槛要一起挂。
- **拿边角工况外推**：样本不足 5 个的工况格子上，模型输出只能当参考——先查覆盖表再用模型。
:::

## 一句话记住

> 模型训练只要几分钟，数据准备要几周——质量在采集端把关、面单在开工前贴好、覆盖按菜单验收、传送带通到训练平台：七项就绪条件是验收清单，不是从训练开始补救的口号。
