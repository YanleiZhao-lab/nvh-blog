# 异响发生那一刻，视频怎么和振动数据对上？——Testlab Neo 视频导入与同步

> 评审会上最常听到也最没用的一句话是"录痕 12 秒那儿有一声异响"：打开 40 通道数据，12 秒附近躺着几十个瞬态峰，哪一个才是那声响？工程师手里其实还有一段现场视频，但视频走的是相机的时钟、数据走的是采集器的时钟——两块从没对过表的秒表，读数没法直接比。本文讲 Simcenter Testlab Neo（2019.1 及以上）的视频导入与同步回放：视频怎样进项目、项目文件为什么不会因此膨胀、两条同步路线（手动对绝对时间、双游标交互对齐）各自适用什么条件，以及一笔帧步进精度账——它决定视频对齐的物理天花板。

::: tip 30 秒速览
- **一句话**：相机拍的画面和采集器存的振动，怎么知道它们说的是同一瞬间的事？
- **类比**：像两块各自计时的秒表——直接比读数没有意义，先得对表：要么把针拨到同一个标准时间，要么让两块表同时看到同一声发令枪。
- **关键数字**：时间偏移猜错 0.35 秒，30 fps 视频里目标画面就差 10 帧、334 毫秒；对准之后残差不到 1 毫秒，但 30 fps 的天花板是半帧 16.7 毫秒。
- **结论**：同步的全部内容就是找出并填对一个时间偏移量；手动填绝对时间最快，双游标对齐最通用；对齐精度永远卡在"半帧"。
:::

## 一、"12 秒那儿有一声异响"这句话，为什么救不了排查

一个典型的异响排查现场：电动车缓慢碾过减速带，车内出现间歇性"咯吱"声。路试团队带回 40 通道录痕和一段用运动相机拍的车内视频，评审意见只有一句"12 秒附近有异响"。打开数据，12 秒前后有底盘冲击、转向器齿条来回打、座椅导轨碰撞等十几个瞬态峰；打开视频，只能听见声音却看不清到底是哪个部件在动。"哪一声"与"哪一帧"之间隔着一条时间轴的鸿沟——**数据有量级没有目击，视频有目击没有量级**，两条证据链对不上，排查就只能靠猜。

Testlab Neo 从 2019.1 版起提供解法：把 mp4 视频导入项目，与振动、声、应变等任何已采集数据同步回放，回放时数据、声音、画面一起动。它解决的正是上面那条鸿沟：**给两条时间轴建立一个换算关系**。

![同步回放：数据、视频与声音同屏联动](/images/neo-video-synchronization/fig1.png)

*（图源：网络 侵删）*

这个换算关系只有一个未知数。视频时钟与数据时钟各自走秒，只要两块表都还算准（短时间内走速一致），两者之间就只差一个固定的开机偏移量 Delta：

这个公式回答的问题是：**视频的第几秒对应数据的第几秒**——同步的全部工作，就是把这一个 Delta 找出来填对。

$$t_{\mathrm{acq}} = t_{\mathrm{vid}} + \Delta$$

其中 $t_{\mathrm{acq}}$ 是数据时间轴上的时刻，$t_{\mathrm{vid}}$ 是同物理瞬间在视频时间轴上的时刻。Delta 的典型来源：相机比采集器早开了几秒、或晚开了几秒。下面先讲视频怎么进项目（第二节），再讲两条找 Delta 的路（第三、四节），最后讲对齐之后回放能干什么（第五节）。

::: info 核心概念
- **视频同步（Video Synchronization）**：在视频时间轴与数据时间轴之间建立确定的偏移换算，使回放、游标、事件定位在两边一致。
- **吞吐文件（Throughput File）**：采集器落盘的原始时历文件（Testlab Neo 中为 .ldsf），与视频文件（.mp4）一起存放在项目同名目录下的 run 子文件夹里。
- **绝对时间（Absolute Time）**：带年月日时分秒（可到纳秒）的墙钟时间。相机与采集器若都记录了可信的绝对时间，Delta 可以直接算。
- **帧率（Frame Rate, fps）**：视频每秒的帧数。帧是视频的最小时间单位，决定了同步精度的物理天花板。
:::

## 二、视频进项目：四步导入与一笔存储账

导入前先开两个插件：在 Desktop 里 File -> Add-ins 勾上 **Video Replay**（12 tokens）做同步回放；若要带声音回放，再开音频回放插件。注意分工：**导入视频本身不需要 Video Replay 插件，交互式同步才需要**。

四步导入链：

1. 在项目树上右键 Run Name，选 **Import**；
2. 文件类型选 *.mp4——这是唯一受支持的格式——按 Open；
3. 视频落入所选 run，按 OK 确认。

![在 Run 上右键选 Import，选中 mp4 后按 Open](/images/neo-video-synchronization/fig3.png)

*（图源：网络 侵删）*

![视频落入所选 run，按 OK 完成导入](/images/neo-video-synchronization/fig5.png)

*（图源：网络 侵删）*

视频来源不限：运动相机、Scope App 手机采集、声学相机（Sound Camera）的素材均可，只要转成 mp4。

::: warning 两个容易踩的坑
- **别去项目文件里找视频**：导入视频后 *.lms 项目文件不会变大。大文件（时历 .ldsf、视频 .mp4）都存在项目同名目录下对应 run 的子文件夹里——Windows 资源管理器里看，就是 *.lms 旁边那个同名文件夹。Single file 的外观、分离存储的实质。
- **格式只有 mp4**：现场用别的格式录的素材，回办公室先转码再导入。
:::

这笔"项目文件不变大"的账值得算一下，因为它决定了备份与搬运策略：项目文件管的是结构（通道表、流程、显示），run 文件夹管的是内容（时历与视频）。同一场 40 通道、20480 Sa/s、1 小时的试验再配一段 65 Mbps 的 10 分钟视频，内容侧的体量是结构侧的 300 多倍——搬数据搬的是文件夹，而不是只拷那个看起来很完整的 *.lms。

结论先摆在这段代码跑出来的数里：时历 11.0 GiB、视频 4.5 GiB，合计 15.5 GiB，是 50 MB 项目文件的 333 倍。

<details>
<summary>数值实验：一场试验的存储分离账（8 行）</summary>

```python
fs, nch, hours = 20480, 40, 1
ldsf = nch * fs * 4 * 3600 * hours / 2**30   # float32 时历，1 小时
mp4  = 65e6 / 8 * 600 / 2**30                # 65 Mbps 视频码率，10 分钟
lms  = 50e6                                   # 典型项目文件大小
print(f"时历 1 h = {ldsf:.1f} GiB；视频 10 min = {mp4:.1f} GiB")
print(f"run 文件夹合计 {ldsf+mp4:.1f} GiB")
print(f"项目文件 {lms/1e6:.0f} MB，内容/结构 = {(ldsf+mp4)*2**30/lms:.0f} 倍")
```

运行输出：

```text
时历 1 h = 11.0 GiB；视频 10 min = 4.5 GiB
run 文件夹合计 15.5 GiB
项目文件 50 MB，内容/结构 = 333 倍
```

</details>

## 三、第一条路：手动同步——两块表都对过标准时间

如果相机与采集器都记有可信的绝对时间（年/日/月/时/分/秒，Testlab Neo 可读到纳秒），Delta 可以直接手填：右键视频选 **Video Time...**，在 Corrected Time Data 栏填入视频的真实绝对时刻，保存即完成同步。

![右键视频选 Video Time，在 Corrected Time Data 填真实绝对时间](/images/neo-video-synchronization/fig6.png)

*（图源：网络 侵删）*

这条路快，但有两个前提经常不成立：相机时钟本身没对过时（运动相机出厂默认时间能差几年）；或视频是从别人手里转来的，绝对时间不可考。**绝对时间可信就用手动，不可信就换交互**——如果对相机的绝对时间没把握，直接走下一节的双游标路线。

## 四、第二条路：双游标交互同步——找那一声发令枪

双游标同步不依赖任何时钟记录，思路回到"对表"的老办法：让两块表同时看到同一个事件。操作链：

1. 按住 Ctrl 同时选中时历数据与视频——两者并排显示；
2. 右键视频选 **Add Video Sync**，两窗各出现一根游标：**红游标钉在数据上、黑游标钉在视频上**；
3. 挪动两根游标，直到它们指向同一物理瞬间（那声"发令枪"：一次敲击、一声咔哒、一个明显脉冲）；
4. 右键视频选 **Sync Video**，软件据此解出 Delta 并锁定。

![Ctrl 多选数据与视频，并排显示](/images/neo-video-synchronization/fig7.png)

*（图源：网络 侵删）*

![右键视频选 Add Video Sync，出现红黑双游标](/images/neo-video-synchronization/fig9.png)

*（图源：网络 侵删）*

选"发令枪"有三个讲究：优先选**又快又硬**的事件（敲击、跌落、金属咔哒），别选缓慢过程；事件两侧留出干净的背景，便于放大后逐帧辨认；**方向键每按一次走一帧**，配合在事件附近拖框放大，是逐帧逼近的标准手法。

![挪动双游标到同一瞬间后，右键 Sync Video 完成对齐](/images/neo-video-synchronization/fig10.png)

*（图源：网络 侵删）*

对齐的天花板由帧率决定，这笔账最好在选相机时就算：视频的最小刻度是帧，30 fps 一帧 33.3 毫秒、半帧 16.7 毫秒——就算游标对得再准，残差最好也只能压到半帧。想再小一倍，帧率加倍。

结论先摆在这段代码跑出来的数里：把开机偏移猜成 2.0 秒（真值 2.35 秒），30 fps 下画面差 10.0 帧、334 毫秒；填对 2.35 秒后帧中心残差 -0.7 毫秒（亚帧级）；而 30/60/120 fps 的半帧天花板分别是 16.7/8.3/4.2 毫秒。

<details>
<summary>数值实验：偏移猜错差多少帧，与半帧精度天花板（22 行）</summary>

```python
import numpy as np
rng = np.random.default_rng(7)
fs = 20480                                # 采样率
t = np.arange(int(fs*20)) / fs
# 12.00 s 处一个 1800 Hz 瞬态"发令枪"，加背景噪声
x = 0.2*np.sin(2*np.pi*1800*t)*np.exp(-((t-12.0)**2)/(2*0.008**2)) \
    + 0.002*rng.standard_normal(len(t))
k = int(np.argmax(np.abs(x[:int(14*fs)])))   # 数据里找到事件时刻
t_ev = t[k]
print(f"事件在数据时间轴上：t_acq = {t_ev:.4f} s")
fps = 30.0
for guess, true in ((2.0, 2.35), (2.35, 2.35)):   # 猜的/真实的开机偏移
    tv = t_ev + guess                     # 该看的视频时刻
    f = int(np.floor(tv*fps))             # 落在第几帧
    err = (f/fps + 0.5/fps) - (t_ev + true)  # 帧中心对事件的残差
    print(f"Delta 猜 {guess:.2f} s：落在第 {f} 帧，残差 {err*1000:+.1f} ms"
          f" = {err*fps:+.1f} 帧")
for f_ in (30, 60, 120):                  # 帧率天花板
    print(f"{f_:3d} fps：半帧量化 = {0.5/f_*1000:.1f} ms")
```

运行输出：

```text
事件在数据时间轴上：t_acq = 12.0007 s
Delta 猜 2.00 s：落在第 420 帧，残差 -334.0 ms = -10.0 帧
Delta 猜 2.35 s：落在第 430 帧，残差 -0.7 ms = -0.0 帧
 30 fps：半帧量化 = 16.7 ms
 60 fps：半帧量化 = 8.3 ms
120 fps：半帧量化 = 4.2 ms
```

读数要点：猜错 0.35 秒 = 差 10 帧——在 30 fps 里相当于画面已经跳过了大半个动作；填对后残差亚毫秒，说明误差来源已从"偏移填错"切换为"帧量化"；最后一行提醒：**同步精度买不到帧率以下**，要更高的对齐精度，只能在拍摄端加帧率。

</details>

## 五、对齐之后：回放、变速与多机位

同步完成后，点左下角播放键，数据、视频、声音一起动——"12 秒那声异响"从此变成"画面里第几秒、哪根曲线抬头"。

![点左下角播放键开始同步回放](/images/neo-video-synchronization/fig11.png)

*（图源：网络 侵删）*

音频回放插件关闭时，回放速度可调快可调慢——对间歇异响，慢放等于把时间轴拉宽，肉眼更容易跟上事件与曲线的联动；赶进度时快放扫全程。

![回放速度控件在播放键旁，可加速可减速](/images/neo-video-synchronization/fig12.png)

*（图源：网络 侵删）*

多机位同样支持：把不同角度的视频都同步到同一数据上，回放时逐一切换视角。电动车声源排查是典型用法——底盘视角、传动视角、内饰视角各对一次表，异响定位从"猜"变成"看"。

## 六、把同步纳入流程的三条工程建议

1. **拍摄端先想对齐**：帧率按需选（对齐精度天花板 = 半帧时长）；开拍前让相机与采集器过同一个绝对时间源，能用第三节手动路就省掉第四节交互路；现场做一次明确的"发令枪"动作（敲一下、喊一嗓），给后期留锚点。
2. **别只拷 *.lms**：视频与时历在 run 文件夹里，备份、移交、上服务器都要连文件夹一起搬（第二节的 333 倍账）。
3. **报告里写清同步方式**：手动填绝对时间还是双游标对齐、锚点事件是什么、帧率多少——同步方式本身就是数据质量信息，复核的人需要它来判断"视频证据"可信到半帧还是到秒级。

## 一句话记住

视频与数据同步的全部内容是填对一个时间偏移量：绝对时间可信就手动填、不可信就用双游标对一声"发令枪"；对齐精度永远卡在半帧——30 fps 就是 16.7 毫秒，要更准，去拍摄端加帧率。
