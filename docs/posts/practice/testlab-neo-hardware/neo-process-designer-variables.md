# 流程搭好了，为什么换批数据就失效？——Testlab Neo Process Designer 与变量化工作流

> 同一条处理流程，第一批数据跑得好好的，换一批通道名不同、转速段不同、试验条件不同的数据就报错或悄悄算错——这不是软件的 bug，而是流程里"写死的东西太多"。Process Designer 把处理步骤连成一条可视化流水线，Process Variables 再把流水线里那些容易变的参数（滤波截止频率、跟踪转速通道、稳速段容差……）抽出来集中成变量表。本文用一条"中央厨房"主线讲清楚：流水线怎么搭、哪些参数最该变量化、变量怎么按通道/工况自动取值、Checks 怎么在流程里自动拦截坏数据，以及 5 次 runup 一键 Run Average 的账怎么算。

::: tip 30 秒速览
- **一句话**：同样的处理步骤，为什么换一批数据就要重新点一遍？
- **类比**：它像一家中央厨房——菜谱（流程）固定，辣度、咸淡（变量）写在墙上的小黑板，换一桌客人只改黑板，不动灶台。
- **关键数字**：5 次重复测量取平均，随机抖动缩到原来的 45%；一份存好的流程文件，下个项目只改 3 个变量就能直接跑。
- **结论**：把"步骤"和"参数"分开——步骤搭一次存成流程，参数抽成变量集中管理，换批数据只改变量不动流程。
:::

## 一、问题出在哪：流程没错，是"写死的参数"错了

一个很典型的现场场景：工程师花了一下午在软件里搭好一条 NVH 处理链——读入时域数据、切出稳速段、算谱图、提 73 阶和 18 阶的阶次切片、出平均曲线和包络——当天的五组 runup 数据一次跑通，报告顺利交出。两周后第二批数据来了：通道命名规则变了（`ACC_left_01` 变成 `LHS_bracket_x`）、稳速目标从 80 km/h 换成 95 km/h、滤波截止频率按新规范要从 400 Hz 挪到 600 Hz。流程一跑，要么直接报错找不到通道，要么更糟——不报错，但按旧参数算出一套没人发现的错结果。

反过来想：处理"步骤"其实一点没变（还是切段-算谱-提阶次-求平均），变的只是三五个"参数"。如果把参数直接写死在每一步的设置对话框里，每换一批数据就要挨个点开找、挨个改，漏改一处就是隐患。Process Designer 与 Process Variables 解决的正是这个拆分：**步骤连成流水线、存成文件；参数抽出来、集中成变量表**。流程文件（`*.process`）交付的是"怎么做"，变量表管理的是"这次用什么值做"。

这个拆分可以写成一个极简的关系——**这个公式回答的问题是：一次数据处理运行，到底由哪些东西拼出来的**：

$$\text{Run} = P_{\text{process}}(D;\ V_{\text{variables}})$$

处理运行（Run）= 流程 $P$ 作用在数据 $D$ 上，中间分号隔开的 $V$ 是变量表。流程固定、数据更换、变量集中——三个角色一次分开，换批数据要动的只剩 $V$。别小看这一行：后面所有机制（变量表、条件化取值、Excel 外置、Checks 阈值上黑板）都是在把越来越多的"会变的东西"从 $P$ 挪进 $V$。

## 二、中央厨房：流程是灶台，变量是墙上的小黑板

把整套机制想成一家**中央厨房**。灶台上的炒菜工序——备菜、下锅、颠勺、装盘——一旦调顺了就不再动，这就是 Process Designer 里连好的处理流水线：每个功能块（方法）是一个工位，块与块之间的连线就是传菜路线，数据从时域输入端流进，顺着连线被切分、计算、汇总，最后从输出端变成谱图、阶次切片和报告素材。

而辣度、咸淡、分量这些"每次可能不一样"的东西，中央厨房不会焊死在灶台上，而是写在一块**墙上的小黑板**上——这就是 Process Variables（流程变量）变量表。今天来的是不吃辣的客人，只改黑板上的"辣度：微辣"，灶台工序一字不动。通道名、截止频率、稳速容差、跟踪方式，都属于黑板上的内容，不属于灶台。

这块黑板还有一个进阶玩法：可以按"这盘菜是谁点的"自动换行——按通道名、按运行工况、按车型颜色，黑板上预先写好一张对照表，流程跑到哪个通道就查哪一行（第四节展开）。后面每节都会回到这条主线：**能固定的进流程，会变的上黑板**。

::: info 核心概念
**Process Designer（流程设计器）**：Testlab Neo 中把数据处理的各个方法（滤波、谱分析、阶次提取、平均……）以功能块形式拖放到画布上、用连线串成处理流程的界面，整个流程可保存为独立的流程文件随项目复用。

**Process Variables（流程变量）**：把流程中多个方法里重复出现的参数（截止频率、通道选择、跟踪转速、段容差等）定义为命名变量，集中在一处定义、一处修改、全流程生效；还可按元数据（通道 ID、DOF、运行名、车型、司机……）条件化取值，或直接从 Excel 表格读取。
:::

## 三、流水线怎么搭：从一段长录痕到一条可保存的流程

先看流程本身。公开技术资料给出的典型 NVH 处理链是这样的：车辆跑一圈，**一段连续长录痕**带回办公室（而不是在每个工况点手动启停采集），流程第一件事就是"切"——按转速/车速条件把长录痕切成一个个稳速段或 runup 段；第二件事是"查"——对切出的段做数据质量检查，不合格的段直接拦下；第三件事才是"算"——对合格段算谱图（spectrum map）、提阶次切片（order section）、做多次运行的平均（Run Average）与包络。报告需要时，FRF、相干、点云图（point cloud map，把任意 NVH 量对转速-功率画散点）也可以作为功能块接到同一条流程上。

切段的判据本身就是变量化的第一候选。下面这个演示回答的问题是：**一段 120 s 的连续录痕里，"稳速段"到底是谁说了算**——判据写死在流程里，换目标车速就失效；判据上了"小黑板"，一条流程通吃两个工况。

<details>
<summary>数值实验：120 秒连续录痕按"目标车速 ±2 km/h、连续 ≥5 s"切段（15 行）</summary>

```python
import numpy as np
np.random.seed(3)
fs = 100
t = np.arange(0, 120, 1/fs)
# 120s 行驶：0-30s 加速到80，30-55 稳80，55-65 加速到95，65-95 稳95，95-120 减速
spd = np.piecewise(t, [t<30, (t>=30)&(t<55), (t>=55)&(t<65), (t>=65)&(t<95), t>=95],
    [lambda x: 80*x/30, lambda x: 80+0.5*np.sin(2*np.pi*0.05*x), lambda x: 80+15*(x-55)/10,
     lambda x: 95+0.4*np.sin(2*np.pi*0.04*x), lambda x: 95-95*(x-95)/25])
spd = spd + np.random.normal(0, 0.35, len(t))
for target in [80, 95]:                       # ← 这两行就是"黑板"：换工况只改这里
    stable = np.abs(spd - target) <= 2.0      # 容差 ±2 km/h
    d = np.diff(stable.astype(int)); starts = list(np.where(d==1)[0]+1); ends = list(np.where(d==-1)[0]+1)
    if stable[0]: starts = [0] + starts
    if stable[-1]: ends = ends + [len(stable)]
    segs = [(s, e) for s, e in zip(starts, ends) if e-s >= 5*fs]   # 最短段长 5 s
    print(f"目标 {target} km/h±2：命中点占比 {stable.mean()*100:.0f}%，>=5s 连续段 {len(segs)} 个")
    for s, e in segs:
        print(f"  段 {s/fs:5.1f}-{e/fs:5.1f} s  时长 {(e-s)/fs:4.1f} s  均值 {spd[s:e].mean():.2f}")
```

运行结果：

```text
目标 80 km/h±2：命中点占比 23%，>=5s 连续段 1 个
  段  29.4- 56.0 s  时长 26.7 s  均值 79.93
目标 95 km/h±2：命中点占比 27%，>=5s 连续段 1 个
  段  64.2- 95.3 s  时长 31.0 s  均值 94.92
```

</details>

同一个 `target` 变量从 80 改成 95，切段逻辑一行没动，两个工况各自的稳速段（26.7 s 与 31.0 s）都被正确切出——这就是"步骤与参数分开"的最小验证。公开技术资料对同一段试车场长录痕给过一个规模参照：一段约 25 分钟、约 1.2 GB 的连续时域记录，流程可以自动切成多组 runup 段做同步阶次跟踪、在预定稳速点做差速器-座椅导轨传递率（FRF）、再做啸叫阶次的声学图谱，全程无人干预。

## 四、变量化：把"会变的"搬上小黑板

哪些参数最该上"小黑板"？工程实践里优先级最高的三类：

1. **通道选择类**：跟踪转速用哪一路（光学/磁电/编码器）、参考通道、输入输出通道对。换批数据最常见的就是通道改名，把它写成变量（或按命名规则的条件变量），流程不用重连。
2. **物理参数类**：滤波截止频率、积分上限、阶次数（比如差速器 73 齿对应 73 阶）、稳速容差与最短段长。规范一换版，这些值集体搬家。
3. **判定阈值类**：Checks 的合格线、包络统计口径。

变量化的收益不只是"少点几次鼠标"：参数集中后，**一次变更全流程同步**，杜绝了"改了滤波块忘了改阶次块"这类最隐蔽的不一致；变量名进流程文件，审阅的人一眼看到这个流程依赖哪些外部输入。

条件化变量（conditional variables）是黑板的进阶形态：变量的取值不再是一个数，而是一张**按元数据查行的对照表**——按通道 ID、DOF、运行名、车型、司机、轮胎品牌、天气取不同的值。公开技术资料举的例子：同一个滤波方法块，截止频率按通道自动调整，不需要为每种传感器复制一条支路；胎压、湿度、声明的车速这类测量元数据也能直接进流程逻辑。甚至整个变量表可以直接放在一张 Excel 里，流程每次运行时现读现用——现场工程师维护表格，分析流程一字不动：

## 五、流程里的质检员：Checks 与平均的账

自动化有一条铁律：**跑得越快，错数据毁得越快**。所以流水线上必须站一位"质检员"——Checks 方法块。它对每一段切出来的数据或每一个算出来的块结果（谱、声压级、阶次切片、FRF）对照设定值或目标曲线做判定，不合格的直接拦下，不允许流向下游。公开技术资料里的例子：对提取出的 runup 段检查车辆加速度变化率，不满足条件的段自动剔除；又如对块数据检查是否落在目标曲线的包络内。再配合按运行标注（descriptive annotation）的机制，检查通过的数据自动打上"质量合格"标记，报告与检索直接受益。

![Checks 方法块：块结果对照设定值/目标曲线自动判定，不合格数据被拦截在流程内](/images/neo-process-designer-variables/fig2.png)

*（图源：网络 侵删）*

质检合格的多段数据进入汇总。Run Average 是阶次分析里最常用的一步：同一工况重复测了 5 次，每次的阶次切片曲线叠在一起总有随机抖动，工程上取平均曲线看趋势、取包络看离散度。这条"平均"的账值得算清楚——**这个公式回答的问题是：N 次重复测量的平均，到底比单次测量"稳"多少**：

$$\sigma_{\bar{x}} = \frac{\sigma}{\sqrt{N}}$$

单次测量的随机散布 σ（标准差），N 次独立重复取算术平均后缩为 $1/\sqrt{N}$。N=5 时缩到 0.45 倍——抖动几乎减半，而包络线（逐点取最大）与均值线的间距保持在单次散布约 1.2 倍的水平，正好承担"最坏情况"的角色。

<details>
<summary>数值实验：5 次 runup 的 73 阶峰值做 Run Average 与包络（12 行）</summary>

```python
import numpy as np
np.random.seed(7)
rpm = np.linspace(500, 3000, 26)
true = 0.12*(1 + (rpm-500)/2500*1.2)          # 假想的 73 阶真实趋势：随转速上升
runs = np.array([true + np.random.normal(0, 0.028, len(rpm)) for i in range(5)])
avg = runs.mean(axis=0); env = runs.max(axis=0)
resid = runs - true
s_single = resid.std()
s_avg = s_single / np.sqrt(5)
print(f"单次随机散布 std      = {s_single:.3f} g")
print(f"5 次均值后散布        = {s_avg:.3f} g  (1/sqrt(5)={1/np.sqrt(5):.2f}, 缩 55%)")
print(f"均值曲线峰值 {avg.max():.3f} g @ {rpm[avg.argmax()]:.0f} rpm；包络线峰值 {env.max():.3f} g")
print(f"包络-均值平均 {(env-avg).mean():.3f} g = 单次散布的 {(env-avg).mean()/s_single:.1f} 倍")
```

运行结果：

```text
单次随机散布 std      = 0.027 g
5 次均值后散布        = 0.012 g  (1/sqrt(5)=0.45, 缩 55%)
均值曲线峰值 0.278 g @ 2900 rpm；包络线峰值 0.312 g
包络-均值平均 0.034 g = 单次散布的 1.2 倍
```

</details>

0.027 g 的单次抖动，平均后剩 0.012 g——这就是"Run Average 一键出结果"背后那条 $1/\sqrt{N}$ 的账。而包络线峰值 0.312 g 与均值峰值 0.278 g 的差距提醒另一件事：**均值管判读、包络管兜底**，两者都要进报告。

## 六、把流程嵌进更大的自动化版图

单条流程文件本身已是可交付物：存档、复用、发给同事。但它在整个测试自动化版图里只是一环。向上游，采集端的 Schedule Designer 把测量任务排成序列清单（任务-动作-重复次数-元数据），其中每个测量任务可以**预先指定一份 `*.process` 流程文件**——数据一下采集硬件，处理就已经开始；如果 Checks 发现数据不合格，司机还没离开试验场就能收到"重测"提示，把"回来才发现数据废了"的返工成本压到最低。向下游，Workflow Automation 把整场试验的数据按流程文件批量处理、汇成一个项目，配合查询把结果自动写进预定义的 Word/PowerPoint 报告；再往下还能自动发布到数据管理平台。变量化工作流在这张网里的位置很清楚：**流程文件是标准件，变量表是每个项目的配置单**——这也正是"AI 就绪数据"路线对测试环节的要求：处理口径一致、元数据齐全、结果可追溯。

::: warning 常见坑
- **变量名对不上**：条件变量按元数据查行，元数据拼写不一致（`Front` 与 `front`）会导致静默查不到行、回退默认值——变量表要和命名规范一起管理。
- **Excel 路径**：外置变量表被移动或重命名后流程仍按旧路径读，换机器运行前先核对路径。
- **Checks 阈值本身也是变量**：阈值写死等于把判定标准藏在流程深处；把它上变量表，规范换版时和截止频率一起改。
- **平均不是万能**：$1/\sqrt{N}$ 只压随机散布，系统性偏差（传感器装错位置）平均五次还是错的——那要靠 Checks 和传递率基准去拦。
:::

## 一句话记住

> 能固定的进流程，会变的上黑板：处理步骤搭一次存成流程文件，通道、频率、容差、阈值抽成变量集中管理——换批数据只改黑板，不动灶台，Checks 站好岗，$1/\sqrt{N}$ 管平均。
