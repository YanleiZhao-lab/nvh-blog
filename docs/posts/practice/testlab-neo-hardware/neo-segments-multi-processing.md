# 一段长时历，怎样按工况切成可复用的数据块？——Testlab Neo Segments 与多段处理

> 一次路试跑下来，得到的往往是一整段几十分钟不停机的连续录痕：加速、稳速、再加速、换挡、过减速带全混在里面。而报告需要的却是"65 km/h 稳速段的频谱""超车工况的阶次切片"这样按工况分好、各自命名的数据块。靠人眼看着屏幕拖选、手动裁剪，一次两次可以，三百次运行就是灾难。本文围绕 Testlab Neo Process Designer 的 Segments 一族方法，把"怎么切"这件事拆开讲清楚：交互拖选适合探索、规则切段适合批量、GPS 位置适合按路段切、Decompose 适合按挡位拆，切完的段怎么各自命名存成独立 run、又怎么接上谱分析流程一键出结果。

::: tip 30 秒速览
- **一句话**：一段连续录下的长时历，怎么自动切成"每一段都是一个工况"的数据块？
- **类比**：它像一根完整的录像带——回放时按"章节"打点，同一段路、同一个挡位的画面归成一集，而不是从头到尾一整卷。
- **关键数字**：300 秒的录痕里，"64~66 km/h、连续 5 秒以上"这个判据只命中 2 段、共 102.6 秒——不到全长的一半，其余时间全是过渡过程。
- **结论**：切段判据不靠人眼靠通道值——把"什么时候算稳速"写成一条规则，软件替你逐帧判定；切出的每段自动命名成独立 run，后续谱分析、阶次提取照单全收。
:::

## 一、为什么"切"是数据处理的第一道工序

一个几乎每个 NVH 工程师都遇过的场景：整车路试回来，硬盘里躺着一段 40 分钟的连续录痕（throughput 时间文件）。试验大纲上写的是"30、50、80、120 km/h 四个稳速工况各取 30 秒做频谱，再取两次全油门加速做阶次分析"。司机确实按大纲开了，但录痕本身是一整段——30 km/h 稳速段、加速段、50 km/h 稳速段、等红灯的怠速段，全部首尾相接地躺在同一条时间轴上。

接下来怎么办？最原始的做法是打开显示，肉眼对着车速通道找"平的地方"，记下起止时刻，手动裁出一小段，存成新文件，命名，再找下一段。四个工况、三个重复、五台样车，就是六十多次手动裁剪。裁错一次（比如把加速尾巴带进了"稳速段"），频谱上就会多出本不该有的低频能量，而没人能从报告上看出这件事。

问题的本质是：**录痕是按时间连续组织的，而分析是按工况离散组织的**。两者之间的翻译工作——"哪一段时间属于哪个工况"——必须有章法地做。这篇要讲的 Segments 一族方法，就是 Testlab Neo Process Designer 里专门干这件事的工具箱：切出来的每一段都是一个带独立命名的 run，可以直接接谱平均、阶次切片等后续方法，也可以单独导出、单独复算。换句话说，切段不是剪辑的苦役，而是把"司机的驾驶动作"翻译成"数据结构"的第一道工序。

切段之后每一段的"身份"怎么记？可以把一段的生成规则写成一行关系——**这个公式回答的问题是：一段数据，到底由哪些东西定义出来的**：

$$\text{Segment}_k = \mathcal{S}\big(t_k^{start},\ t_k^{end},\ \text{name}_k\big) \subset \text{Run}$$

每一段 $k$ 由起止时刻和名字定义，是原 run 的一个子集。整族切段方法干的事，就是把右边这三个量的"来源"从人眼换成机器：交互拖选让 $t^{start}$、$t^{end}$ 来自鼠标，规则切段来自通道值越过的门槛，位置切段来自 GPS 触发线，Decompose 来自索引通道的取值。下面按这四条路线逐一展开。

## 二、录像带与章节：段是"按内容归档"的回放单元

把整段连续录痕想成**一根完整的家庭录像带**。带子本身从头到尾一秒不落（这就是 throughput 文件：所有通道、全部时长、原样保存），但没有人会从头看 40 分钟——你会按"章节"跳着看：孩子生日那段、海边那段、毕业典礼那段。

Segments 做的就是"打章节点"这件事，而且打点的依据不是时间，而是**内容**：车速稳在 65 km/h 附近的那一段、扭矩超过 100 N·m 的那一段、车开过厂区门口那条减速带的那一段。每个章节（segment）有自己的名字（比如 `Runup_01`、`Steady65_A`），切完之后各自成为一个独立 run，结构上和现场手动启停采集得到的 run 没有区别——后续处理流程完全不区分这两者的出身。

这个类比还有一层：录像带的章节可以**重打**。第一遍按车速切了四章，后来发现报告还想要按挡位的分法，重新定义章节就是了，带子（原始录痕）永远不动。切段方法输出的都是"新文件只含原文件的一段"，原始 throughput 始终是底稿——这既是数据安全的底线，也是"一段录痕支持多套切法"的前提。后文每一种方法都会回到这条主线：**带子不动，章节随定义变**。

::: info 核心概念
**Throughput 文件（吞吐文件）**：采集期间不停机连续记录下来的原始时间数据文件，所有通道全程原样保存，是切段操作的底稿。

**Segment（段）**：从一段连续时间数据中按规则截取的子集，拥有独立的起止时刻与命名，切出后以独立 run 的形式参与后续处理。

**Run（运行）**：Testlab 数据组织里的基本试验单元，一次采集或一次处理的结果都挂在 run 下；切段方法可以"一次输入、多个 run 输出"。
:::

## 四、交互拖选：手动切段的规范做法

即使是最"手工"的拖选，Testlab Neo 也给了规范路径，而不是靠导出再裁剪。在时间历程显示里，按住 **Ctrl + Alt** 同时从左到右拖动，就高亮出一个段（图 2）；只按 Ctrl 不按 Alt，则单选一段。多个段可以连续这样选中。

![在显示中按住 Ctrl+Alt 拖动高亮出段](/images/neo-segments-multi-processing/fig2.png)

*图 2 按住 Ctrl 与 Alt 同时从左到右拖动即可选中段（图源：网络 侵删）*

选好后点击流程里的 **Input** 方法，会弹出"Overwrite Segments"确认（首次出现，之后静默更新）。双击 Input 方法打开属性页，有两个关键设置：

- **Input Data 字段改为 Save in Run**：让每个选中段各自生成一个独立 run，而不是都挤在一个输出里；
- **Segments 后面的 "…" 按钮**：打开段列表，在 **Run suffix** 一栏给每段起名字——处理完成后 run 就叫这个名字，`Runup_01`、`Steady65_A` 之类，报告里一眼可辨。

如果同一段判据在不同录痕里发生在不同时刻（比如"司机踩下油门的瞬间"每次录的位置都不一样），把 **Segment Mode** 从 All Runs 切到 **Per Run**（图 4）：段列表第一列变成 run 选择下拉，逐 run 各设一段。

![Segment Mode 从 All Runs 切换为 Per Run](/images/neo-segments-multi-processing/fig4.png)

*图 3 逐 run 设置不同时间段的 Segment Mode 切换（图源：网络 侵删）*

配合 Data Selection 区把 run 加入 Input Basket、按 Run 运行流程，多段多 run 就一次跑完。交互拖选的产出与后续所有自动化切法完全同构——这也是它作为"规范手动法"的价值：今天手动切的段，明天可以把判据固化成规则交给软件。

## 五、规则切段：把"稳速"写成一条判据

交互拖选的前提是人看得出来"哪一段是稳速"。但稳速的本质是**车速通道的数值落在一个窗口里**——这件事完全可以写成规则，让软件逐采样点判定。这就是 Extract Segments (Rule-Based) 方法：它按某个参考通道的数值条件自动识别段，无需人工干预。典型判据如"车速在 64~66 km/h 之间"——围绕 65 km/h 目标值留 ±2 km/h 容差。

先把一笔账算在前面：一条 300 s 的录痕里，这个判据到底能切出多少东西？下面这段演示回答的问题是——**"64~66 km/h 且连续 5 s 以上"这条规则，在一段典型路试录痕里的命中率是多少**。

<details>
<summary>数值实验：300 秒录痕按"64~66 km/h、连续 ≥5 s"规则切段（18 行）</summary>

```python
import numpy as np
np.random.seed(7)
fs = 100
t = np.arange(0, 300, 1/fs)
# 300 s 行驶录痕：0-40 s 加速到 65，40-100 s 稳在 65（±1.5 抖动），
# 100-130 s 加速到 110，130-220 s 稳在 110，220-260 s 减速，260-300 s 再稳 65
spd = np.where((t >= 40) * (t < 100), 65 + 1.5*np.sin(2*np.pi*0.03*t),
      np.where((t >= 100) * (t < 130), 65 + 45*(t-100)/30,
      np.where((t >= 130) * (t < 220), 110 + 2.0*np.sin(2*np.pi*0.02*t),
      np.where(t >= 260, 65 + 1.5*np.sin(2*np.pi*0.03*t), 65*t/40))))
seg = np.abs(spd - 65) <= 2.0                     # 规则：64~66 km/h
idx = np.flatnonzero(np.diff(np.concatenate(([0], seg.view(np.int8), [0]))))
bounds = idx.reshape(-1, 2)                       # 各段 [起, 止) 采样点
keep = bounds[(bounds[:,1]-bounds[:,0])/fs >= 5.0]  # 最短时长 5 s
for i, (a, b) in enumerate(keep):
    print(f"段{i+1}: {a/fs:.1f}~{b/fs:.1f} s  时长 {(b-a)/fs:.1f} s")
print(f"共 {len(keep)} 段，合计 {sum(b-a for a,b in keep)/fs:.1f} s / 全长 300 s")
print(f"段1 平均速度 {spd[keep[0,0]:keep[0,1]].mean():.2f} km/h")
```

</details>

运行结果：300 s 录痕里命中 2 段——38.8~101.3 s（62.6 s）与 260.0~300.0 s（40.0 s），合计 102.6 s，占比 34%；段 1 平均速度 64.91 km/h。**一半以上的录痕其实是加速、减速的过渡过程，根本进不了稳速分析**——这就是为什么"一刀切整段算频谱"的做法会把过渡段的非平稳能量混进结果，而规则切段天然把这部分挡在门外。

在软件里，这套判据落在方法的属性页（图 5~图 7）：参考通道选车速通道，规则类型选 **Extract**（数值落在两个值之间），写 64 与 66——注意数值必须**带工程单位**（km/h、Nm、rpm），大小写要和显示里 Y 轴图例的写法逐字一致，字段是大小写敏感的。Detection Mode 选 **First Occurrence**（只取第一处）或 **All Occurrences**（所有命中段；还可进一步选 Join 把多段并成一个 run，或 Separate 各自成 run）。

### 两个条件怎么办：先造索引通道

单一门槛只认一个通道。想要"转速超 3500 rpm **且** 扭矩超 100 N·m"的段，就轮到 **Calculate**（时域计算）方法出场：先用它造一个 0/1 的**索引通道（Index Channel）**——默认 0，两个条件同时满足时为 1——再把规则切段指到这个索引通道上，门槛取 0.5（起点要求上斜坡、终点要求下斜坡）。同一套思路也能接住采集时键盘录入的事件标记/评分（Time Data Acquisition 的 marker 与 ratings 功能），司机在采集 PC 上敲的数字键随数据一起记录，事后同样能变成切段判据。

![Calculate 方法造索引通道：扭矩超 100 Nm 且转速超 3500 rpm 时输出 1](/images/neo-segments-multi-processing/fig13.png)

*图 6 双条件索引通道：转速（绿）与扭矩（红）同时超限时索引通道（蓝）为 1（图源：网络 侵删）*

这个"造中间判据通道"的做法值得多看一眼——它把切段判据的表达能力从"一个通道一个门槛"扩展到"任意逻辑组合"，而下游所有方法都不用改。多条件切段的账同样可以算清楚：一段 300 s 的录痕里，"转速 >4500 rpm 且扭矩 >100 N·m"联合判据只命中 160~230 s 一段、共 70 s（段内平均转速 5204 rpm），占全长 23%——两个条件一叠加，可用数据比单条件又少了一截，试验大纲里规定的采集时长要为这类叠加判据留够余量。

## 六、按位置切：GPS 触发线把"路段"变成判据

稳速看车速、超车看扭矩，但"厂区门口那条粗糙路面"既不是车速段也不是扭矩段——它是**地理位置**。Split by Position 方法用 GPS/GNSS 位置当判据：在 Google Earth 里沿目标路段的首尾各画一条触发线（每条线由两个点定义），车每次压线，软件就知道"章节开始/结束"了。

触发线的命名是一门小语法，格式 `名称:中间:结尾`，用冒号分隔三段：

- **名称**（如 `Euclid_Road_North`）：自由命名，切出的段就叫这个名字；
- **中间**：`*` 表示无条件触发（适合作起始线）；数字则表示"只有上一条压过的线是编号 X 的线，本线才生效"——用来串联顺序路段；
- **结尾**：触发线的编号；**正数表示压线后开始存数，负数表示压线后停止存数**（结束线就取 -1，好记）。

例如起始线命名 `Euclid_Road_North:*:1`（无条件触发、编号 1、开始存数），结束线命名 `Euclid_Road_North:1:-1`（承接编号 1、停止存数）——车压过起始线开始记录，压过结束线停止，切出的段自动命名为 `Euclid_Road_North`。

操作链路是：把录痕的 GPS 数据导出成 KML → 在 Google Earth 新建工程并导入，沿着轨迹在路段首尾画两条触发线并按上述规则命名 → 删掉 KML 里的 "Gps Points" 与 "Gps Track"（只留触发线）→ 导出触发线 KML → 在 Split by Position 方法的 Track Definition 参数里选这个文件 → Run。切出的段存在以触发线名命名的 run 里，其下的 Process 文件夹装着切出的数据。注意 Google Earth 显示默认不随 Testlab Neo 开启（出口管制），符合条件时可向销售/支持渠道申请授权。

![GPS 轨迹（红线）与目标路段（黄色括号段）](/images/neo-segments-multi-processing/fig17.png)

*图 7 地图上红色为实测 GPS 轨迹，黄色为待切取的目标路段（图源：网络 侵删）*

按位置切段最典型的用途是**路面对比**：同一条试车路，"光滑段"与"粗糙段"各画一对触发线，一台车跑三圈，就得到六个命名规范的数据块——直接进谱平均流程，出"两种路面对同一辆车振动响应"的对比报告。位置判据与转速、扭矩判据可以各自独立切同一份录痕（带子不动、章节随定义变），报告想怎么组合都行。

## 七、按状态拆：Decompose 与函数域取段

第四条路线解决"状态"维度的切分。一条 900 s 的温度录痕里，挡位通道在 0~5 之间跳变——每个挡位对应一段连续的"状态窗口"。**Decompose** 方法（Interactive Analysis add-in）按索引通道的取值把整条录痕拆开：挡位通道有 6 个值，就输出 6 条新迹线，每条只含对应挡位期间的数据。拆完每条迹线内部的样本来自原录痕的不同时间段（同一挡位的各次出现被"缝"在一起），方法还提供 Fading mode 让缝合处以淡入淡出方式衔接——对声音、振动数据尤其有用，硬拼接会在接缝处产生假瞬态。

![900 秒温度录痕按 6 个挡位 Decompose 成 6 条独立迹线](/images/neo-segments-multi-processing/fig28.png)

*图 8 原 900 s 温度记录按挡位分解为 6 条记录，温度量级随挡位升高（图源：网络 侵删）*

这笔账算出来很直观：整车 900 s 行驶、每挡 150 s，温度从一挡的均值 40.6 °C 爬到六挡的 79.4 °C，而整条录痕的总平均只有 60.0 °C——**任何一个"整段平均"都会把六个热状态糊成一个没有物理含义的数**，Decompose 之后"每挡平均温度"才成为可读的工程量。挡位如此，驾驶模式（经济/运动）、混动模式（纯电/混动）同理：凡是记录成离散状态通道的，都能这样拆。

最后一个近亲方法 **Extract Segment (Block)** 把同样的思路搬到**函数域**：在频谱上取 10~140 Hz 的 RMS、在阶次切线上取某转速区间的均值。显示里用 Double X 光标可以快速读一次，但要对几百个通道批量算并导出 Excel，就把它接在 Spectrum average 之后，Segment start/end 填 `10 Hz`、`140 Hz`（同样必须带单位；阶次函数则是 rpm）——批量统计一次跑完。

## 八、切完之后：段的存储结构与后续流程

所有切段方法共用同一套输出结构：切出的数据存在一个新 run 里（通常在 Process 文件夹下），并常伴有指向原始 throughput 的链接。在显示里选中整个 run 时，原始数据与切出段会叠加出现——**只想看切出的段时，单独选中 Process 文件夹**即可。若希望结果里干干净净只有切出段、不带原始数据链接，把 Input 方法的 Input Data 从 Save time data as link 改为 Do not save。

段的使命在切出来之后才真正开始：谱平均、总级、阶次切片等方法直接接在切段方法之后，形成"切段 → 谱图 → 阶次"的完整流水线。以文章开头那份试验大纲为例，一条流程就能交代：Input（含段定义）→ Spectral Map（Tracking strategy 设 Tracked on Channel、选转速通道、设跟踪上下限）→ Order Sections（跟踪通道 + 阶次列表，如 `2;4;6`）→ Run。多 runup 的 throughput 文件按前文 ctrl+alt 拖选切出三段、各配 Run suffix，一次 Run 全部处理完，每段的谱图与阶次切片按段名归档。

到此可以把切段放回更大的版图里：段的判据（目标车速、扭矩门槛、转速窗）正是流程里"最容易变的参数"，把它们交给 Process Variables 变量表管理，一份流程文件就能通吃不同批次的数据；切出的段按规范命名后，Data Queries 按元数据检索才有的放矢。切段是这条自动化链条的第一环——**切的章法，决定了后面所有自动化能不能跑起来**。

## 九、避开三个坑

::: warning 现场易踩的三个坑
- **判据不带单位或大小写不符**：规则切段与块提取的数值字段必须带工程单位（km/h、Nm、Hz、rpm），且大小写与显示 Y 轴图例逐字一致——字段大小写敏感，`Km/h` 与 `km/h` 不互通；
- **过渡段混进稳速段**：±2 km/h 容差不加"连续 ≥5 s"最短时长约束时，加速过程穿过 64~66 km/h 窗口的 1~2 秒也会成段——判据里永远带最短时长；
- **Google Earth 导出前忘删点与轨迹**：网页版 Google Earth 导出 KML 前必须删除 "Gps Points" 与 "Gps Track"，只留触发线，否则 Split by Position 读不到想要的触发器定义。
:::

## 一句话记住

录痕按时间连续、分析按工况离散——切段就是把车速、扭矩、位置、挡位这些通道值写成判据，让软件替人眼逐帧判定；切出的段独立命名成 run，原始录痕永远不动，一条流程从切段直接跑到阶次切片。
