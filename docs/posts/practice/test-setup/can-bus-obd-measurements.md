# CAN 总线与 OBD-II 测量：车上数据的第二通道

> 整车路试做到一半，工程师发现没有地方装转速传感器：发动机舱已经封好，飞轮外壳找不到开孔位置，专用支架来不及加工。但车上的 ECU 每时每刻都在广播发动机转速、车速、油门开度——这些数据就在 CAN 总线上流着，只差一根线把它引出来。本文讲怎么把 CAN/OBD-II 的车上数据变成 NVH 测试里的一条“第二通道”：报文如何变成工程量、为什么插值与时间戳决定了转速迹线的质量、恒定报文速率在高转速下的角度分辨率代价，以及在 Testlab 里从 DBC 到阶次分析的完整链路。

## 一、为什么需要车上的数据：NVH 测试的“第二只眼睛”

一辆车在粗糙路上做路噪测试，振动加速度计和麦克风记录的是“结果”——车身振动多大、车内多吵；但要把这些结果归因，还需要“原因”侧的信息：当时车速多少、发动机转速多少、挡位是几挡、油门开度多大。同样的 4 阶轰鸣，2000 rpm 定油门与急加速 2000 rpm 瞬间，机理与整改方向完全不同。

这些工况参数恰恰不需要自己去测。现代汽车上的电子控制单元（ECU）之间靠总线通信，发动机 ECU 知道转速，变速箱 ECU 知道挡位，ABS 知道轮速，电池管理系统知道 SOC——它们把各自的状态按固定周期广播到总线上。对测试工程师而言，这相当于一辆车自带了几十条“免费传感器通道”，问题只是如何接入采集系统并与振动数据对齐时间轴。

::: info 核心概念
- <strong>CAN 总线（Controller Area Network）</strong>：车上电子单元之间的串行通信总线，报文按标识符优先级广播发送，无主机
- <strong>OBD-II（On-Board Diagnostics II）</strong>：法规强制的车载诊断接口，标准化了物理插头与基础诊断服务，可读取转速/车速等工况参数
- <strong>DBC 文件（database for CAN）</strong>：描述报文布局的数据库文件——哪个 ID 的哪几位字节是什么物理量、按什么规则换算
- <strong>报文速率（message rate）</strong>：ECU 广播某条报文的频率，如发动机转速报文典型为每秒 10~100 次
:::

传统方案里这些量靠磁电/光电传感器测转速、霍尔开关测挡位，每装一个都要支架、开孔、布线。CAN 通道方案把整辆车变成传感器的延伸：一根四芯线缆，接进 OBD-II 诊断座或并接在动力 CAN 上，就能同时拿到十几个工况参数。工程上称它为 NVH 测试的“第二只眼睛”——第一只眼睛看响应，第二只眼睛看工况。

## 二、把报文变成工程量：从 0x01 0x8C 到 198.0 rpm

CAN 总线上跑的不是工程量，而是打包成帧的二进制数。一帧报文的核心字段是标识符（ID）与数据域：ID 决定这帧报文“是谁发的、优先级多高”，数据域最多 8 个字节装着若干个信号（signal）。要把它变回工程量，需要三步：按 DBC 定义定位信号的字节与位、解出原始整数、做线性换算。

这个公式回答的问题是：报文里那串原始字节如何变成带单位的物理量。其中 raw 是从数据域按起始位和长度解出的整数值，factor 与 offset 是换算系数，physical 就是工程值。

$$
\mathrm{physical} = \mathrm{raw} \times \mathrm{factor} + \mathrm{offset}
$$

例如某车型发动机转速报文数据域前两字节为 0x01 0x8C，按大端拼成整数 396，若 DBC 中定义 factor=0.5、offset=0，则物理值为 198.0 rpm——若 factor 是 0.25 则是 99.0 rpm，同一个字节序列、不同的 DBC 条目给出的读数完全不同。这就是为什么 CAN 测量的第一步永远是拿到正确的 DBC 文件或逐条核实报文定义：换算系数错一倍，后面所有阶次分析全部作废。

经典 CAN 2.0 数据帧的字段结构如下：帧起始、11 位标识符、控制域、最多 8 字节数据、CRC 校验、应答与帧结束，最坏情形（含位填充）约 130 余位。在 500 kbps 的典型车用速率下，一帧最长报文的传输时间约 260 微秒——对 NVH 测量而言这个延迟可以忽略，真正要关心的是后面两节讲的报文间隔与时间戳。

可以把整车想象成一栋子各说各话的公寓洼青年：每个人（ECU）隔一会儿就在门厅喊一声“我这里转速 1980、水温 88”（广播报文），声音大小（ID 优先级）决定同时开口时谁先说（总线仲裁），没人回应就重说一遍（自动重发）。测试工程师就是坐在门口的记录员：不参与对话，只把每句话连时间戳带内容记下来，事后按需要查阅。公寓里没有“主人”，也不需要向谁申请发言——这就是 CAN 无主机广播机制的直观图景，也是它与请求-应答式诊断接口最大的不同。

## 三、时间轴上的第二通道：插值、时间戳与转速迹线质量

把 CAN 报文接到采集系统后，软件拿到的是一串“时间戳 + 工程值”的离散点，比如每 50 ms 一个转速值。而振动通道的采样率通常是 1024 Hz 以上。两者要在同一时间轴上对齐，就需要在报文点之间插值，把低速率的 CAN 信号变成与振动通道同采样率的连续迹线。

插值本身不制造信息，它只是把缓变曲线补光滑。这个公式回答的问题是：任意时刻 t 的转速值由哪两帧报文决定、各占多少权重。t1、t2 是相邻两帧报文的时间戳，v1、v2 是对应的工程值，权重由 t 在两帧之间的相对位置给出。

$$
v(t) = v_1 + (v_2 - v_1)\,\frac{t - t_1}{t_2 - t_1}, \quad t_1 \le t \le t_2
$$

真正决定转速迹线质量的是三个误差源，而且它们的重要性经常被低估：

- <strong>量化误差</strong>：raw 是整数，换算后物理值的台阶就是 factor。factor=0.5 rpm 时转速读数永远落在 0.5 rpm 的整数倍上。对缓变工况它只是小锯齿，但扭振分析要的恰恰是围绕均值的微小波动，量化台阶会直接混进扭振谱
- <strong>报文速率</strong>：20 Hz 的报文率意味着转速迹线的有效更新间隔 50 ms。在急加速工况（例如 3000 rpm/s）下，50 ms 内转速已经变化 150 rpm——插值只能连直线，追不上真实曲线的弯曲
- <strong>时间戳抖动</strong>：报文从 ECU 发出、经总线仲裁排队、被采集卡打上时间戳，每一环都带几毫秒的随机抖动。抖动会被上式的斜率项放大：转速变化越快、抖动引起的误差越大

下面的数值实验把三个误差源拆开看。缓变转速（0.2 Hz 正弦、幅值 300 rpm）下，20 Hz 报文 + 1 rpm 量化时插值迹线的最大误差只有 0.47 rpm；叠加 ±5 ms 时间戳抖动后误差升到约 1.9 rpm——抖动比量化更伤。

![20 Hz CAN 报文量化值与插值后的转速迹线](/images/can-bus-obd-measurements/fig1-rpm-from-can.png)

*（图源：网络官方公开资料）*

把四种报文速率下“无抖动”与“±5 ms 抖动（20 次平均）”的最大误差画在一起，结论更直观：报文速率从 10 Hz 提到 100 Hz，无抖动误差从 0.94 rpm 降到 0.17 rpm，收益明显；但只要时间戳带着 5 ms 抖动，10 Hz 时误差被放大到 6 rpm 以上，且低速率段抖动的影响远大于量化。

![时间戳抖动在不同报文速率下的转速误差放大效应](/images/can-bus-obd-measurements/fig2-jitter-error.png)

::: warning 工程注意
用 CAN 转速做扭振或高频阶次分析前，先确认三件事：报文速率多高（决定信息上限）、量化台阶多大（factor 值）、时间戳是硬件打的还是软件打的（软件打戳在总线负载高时抖动可达毫秒级）。三件事任何一件不达标，CAN 转速只能做工况记录，不能进阶次分析。
:::

## 四、恒定报文速率的隐性代价：每转帧数随转速下降

CAN 报文按时间等间隔发送，而阶次分析需要的是角度轴上的信息密度。这两个坐标系的错位，是 CAN 转速通道最容易被忽视的限制。

这个公式回答的问题是：在给定转速下，每转能拿到几帧报文。n 是转速（rpm），f_msg 是报文速率（帧/秒）。注意分母是转速——转速越高，每转时间越短，帧数越少。

$$
N_{\mathrm{frame/rev}} = \frac{f_{\mathrm{msg}}}{n/60}
$$

代入具体数字：20 Hz 的转速报文，800 rpm 时每转 1.5 帧（角度步长 240 度），2000 rpm 时每转只剩 0.6 帧，6000 rpm 时 0.2 帧——每转连一帧都凑不齐。对比阶次分析的习惯要求（扭振分析通常要求每转至少几十个样本、能分辨的最高阶次约为每转帧数的一半），CAN 转速在高于怠速的绝大多数区间都远远不够。

![不同报文速率下每转帧数随转速的下降](/images/can-bus-obd-measurements/fig3-frames-per-rev.png)

*（图源：网络官方公开资料）*

这个限制划出了 CAN 转速通道的适用边界：做工况标记（转速区间、挡位、油门状态）、colormap 的转速轴、低阶量级的趋势分析——够用；做扭振、高阶次切片、需要精细角度分辨率的分析——必须回到物理转速传感器（每转几十到几百个脉冲）。这不是 CAN 的缺陷，而是“时间等间隔采样”与“角度等间隔采样”两种坐标系的本质差异。

## 五、OBD-II 与原生 CAN：两条接入路径的取舍

接入车上有两条路，工程性质不同。

第一条是 OBD-II 诊断座。1996 年起法规强制所有乘用车装备标准化诊断座（16 针、驾驶侧仪表下方），通过诊断服务协议读取数据：测试设备发送请求，ECU 响应应答。优点是完全标准化——不需要车型的 DBC，任何车都能读到一组法定基础参数（发动机转速、车速、冷却液温度等）；缺点是请求-应答模式跑在诊断协议栈上，有效数据速率低（通常每秒几组到几十组），且读取速率受 ECU 诊断服务实现限制。这条路适合数据记录、工况标记、对照校核。

第二条是并接原生 CAN 总线（常经网关或 OBD 座上的 CAN 引脚）。测试设备像车上另一个节点一样监听总线广播，ECU 发什么就收什么。优点是全速率——转速报文可以到 100 Hz，且能拿到 DBC 里定义的一切信号（扭矩、点火角、电机转矩、挡位……）；缺点是需要车型的 DBC 文件与总线物理参数（500 kbps 高速 CAN 或 250 kbps），部分网关对外只开放过滤后的子集。这条路是 NVH 阶次分析的标准配置。

| 维度 | OBD-II 诊断协议 | 原生 CAN 并接 |
| --- | --- | --- |
| <strong>接入方式</strong> | 诊断座 + 请求/应答 | 并接总线、监听广播 |
| <strong>标准化程度</strong> | 法定统一参数集 | 按车型 DBC 定义 |
| <strong>有效速率</strong> | 每秒几组~几十组 | 报文原生速率（可到 100 Hz+ |
| <strong>信号丰富度</strong> | 基础工况参数 | DBC 内全部信号 |
| <strong>适用场景</strong> | 工况记录、快速排查、无 DBC 的车 | 阶次分析、TPA 工况输入、正式路试 |

两条路径不互斥：正式路试常用原生 CAN 做正式通道，OBD-II 读取同参数做交叉校核——两个独立来源的转速对得上，才放心把工况标签贴到数据上。

## 六、Testlab 中的操作链路：从 DBC 到阶次切片

在 Simcenter Testlab 中，CAN 通道的配置集中在 Channel Setup 的总线通道区：加载 DBC 文件后，报文里的每个信号变成一个可选通道，勾选即进入测量通道列表，采样率与量程换算由 DBC 条目自动带入。采集时硬件（如 SCADAS 的 CAN 调节单元，每台可接 4 条 CAN 总线，支持 CAN 2.0B 与 CAN FD）在后台完成报文接收、解码与时间戳标记，CAN 通道与模拟通道在同一条数据流里同步存储。

后处理链路与普通转速通道一致：CAN 转速迹线可直接作为 Tracking Setup 的跟踪源做阶次分析，也可在 Time Signal Calculator 里参与公式运算。需要人工插值/重采样时，按指定输出采样率重建连续迹线，原理即上述线性插值式。

三个实操要点。其一，DBC 与实车对不上时（读数明显异常），先用 OBD-II 诊断读同参数做对照，定位是 DBC 版本错还是字节序/换算系数错。其二，多 CAN 段（动力 CAN、底盘 CAN 经网关转发）的信号时间戳经过网关会带额外延迟，跨段信号不要用来做严格同步的互相关。其三，正式测量前录一段已知工况（定转速台架或定速巡航），核对 CAN 转速与仪表/独立传感器的一致性，偏差应小于一个量化台阶。

## 七、numpy 数值实验：三个误差源一次算清

```python
import numpy as np

fs = 100.0                                    # 目标输出采样率
t = np.arange(0, 10, 1/fs)
true_rpm = 1800 + 300*np.sin(2*np.pi*0.2*t)   # 缓变真实转速

msg_hz = 20.0                                 # 报文速率 20 Hz
nmsg = int(10*msg_hz) + 1
tmsg = np.arange(nmsg)/msg_hz                 # 报文时间戳
rpm_q = np.round(1800 + 300*np.sin(2*np.pi*0.2*tmsg), 0)  # 1 rpm 量化

err0 = np.abs(np.interp(t, tmsg, rpm_q) - true_rpm).max()
print(f"quant 1 rpm, no jitter : max err = {err0:.2f} rpm")

jit = np.random.default_rng(1).uniform(-0.005, 0.005, nmsg)
errj = np.abs(np.interp(t, tmsg + jit, rpm_q) - true_rpm).max()
print(f"with +-5 ms jitter     : max err = {errj:.2f} rpm")

for n in (800, 2000, 6000):                   # 每转帧数 vs 角度步长
    fpr = msg_hz/(n/60)
    print(f"rpm {n:5d}: {fpr:5.1f} frames/rev, angle step {360/fpr:6.1f} deg")
```

运行输出（本机实测）：

```text
quant 1 rpm, no jitter : max err = 0.47 rpm
with +-5 ms jitter     : max err = 1.92 rpm
rpm   800:   1.5 frames/rev, angle step  240.0 deg
rpm  2000:   0.6 frames/rev, angle step  600.0 deg
rpm  6000:   0.2 frames/rev, angle step 1800.0 deg
```

量化 1 rpm、报文 20 Hz 的“理想”配置下插值误差不到半个 rpm；引入 ±5 ms 时间戳抖动后误差翻四倍；而每转帧数一栏直接给出判决——2000 rpm 每转 0.6 帧，连一转一帧都保证不了，这类迹线只能做 colormap 的转速轴与工况标记，不能做扭振。

## 八、小结

CAN/OBD-II 通道的本质，是把车上已有的传感器与计算结果（ECU 内部的转速估计、挡位判断）通过广播报文“借”给测试系统。用好它需要三层认识：数据层——DBC 换算系数决定读数对错，第一步永远是对表；信号层——量化、报文速率、时间戳抖动三个误差源决定迹线质量，抖动常被低估；应用层——时间等间隔的报文在高转速下每转帧数骤降，CAN 转速适合工况记录与转速轴，扭振与高阶次分析仍需物理转速传感器。两条接入路径（OBD-II 诊断、原生 CAN 并接）按标准性与速率取舍，正式路试双路并用交叉校核。

## 一句话记住

CAN 报文是时间轴上的工况记录而非角度轴上的测量：DBC 定读数对错，报文速率定信息上限，每转帧数随转速降——工况标记用 CAN，扭振与高阶次还是要装传感器。
