# SCADAS RS 故障排除：LED 状态/网络/数据传输诊断树

> 路试第一天早上，REC 单元的指示灯在快闪红色：是硬盘满了，还是菊花链超了吞吐量？两者共用同一种灯色，答案却在完全相反的方向：前者删数据就能继续，后者必须降采样率或拆链。更隐蔽的是「什么都正常却连不上」：单元状态灯绿色慢闪（一切正常），Web 应用却打不开，病根可能在 PC 的 SSDP 服务、公司网禁了 LLMNR、或者干脆是浏览器缓存了升级前的旧页面。SCADAS RS 的故障指示是一套「颜色 x 闪烁频率」的编码语言，读不懂它，现场就只能反复断电重启。这篇把 LED 状态表、第 16 章故障排除表和网络三层（发现、连接、传输）拆成一棵能按图索骥的诊断树，配一个「医院分诊台」的类比：分诊护士（指示灯）先按症状分级，再决定挂哪个科室（电源/网络/吞吐/存储），而不是一上来就返厂。附一段 numpy 代码把灯语判定逻辑写成可跑的分诊函数。

## 一、为什么「灯语」值得先学：一个真实的排查现场

先看一个典型场景。某车队路试，早班司机反映「设备昨晚还好好的，今天状态不对」。工程师到现场，看到 REC 单元前面板一颗状态灯在**快闪红色**。他的第一反应是坏了，准备拆机换备件。但翻到状态表：快闪红色对 REC 单元有两种含义：**数据存储几乎已满**，或**一个或多个菊花链超出吞吐量**。前者清掉 SSD 就能跑，后者要查通道采样率配置。两种「病」共用一种「症状」，区分靠的是问诊：Web 应用里看存储剩余量（几分钟），再看链路吞吐统计（每链上限 1.7 MSa/s、REC 总计 7.8 MSa/s）。十分钟后定位是夜间未关机持续录制把 SSD 写满，删数即愈。如果没有这套灯语知识，这台设备当天就上不了车。

这就是 SCADAS RS 故障排除的第一个原则：**面板上的每颗灯都在说一种受限的语言，读懂它，多数故障能在现场闭环**。设备相关技术手册第 16 章把常见故障压成一张「状态/错误条件、可能原因、解决方案」的三列表，但直接背表是低效的；高效的读法是先理解 LED 编码体系（第 12 章），再用它给故障分型，最后才落到第 16 章的表里查细项。

打个贯穿全文的比方：这套体系像**医院急诊室的分诊台**。患者（故障设备）走进来，分诊护士（面板指示灯）不治病，只做三件事：看脸色（灯色：绿/黄/红/青/白/品红）、量脉搏（闪烁频率：固体/正常/快/慢）、决定送哪个科室（电源科、网络科、吞吐科、存储科）。灯色对应严重程度：绿色是「可以候诊」，红色是「需要干预」；闪烁频率对应状态机的相位：固体（稳态）多为「正在发生」，快闪多为「等待处理或告警」，慢闪多为「休眠」。分诊错了科室，后面的检查全白做；灯读错了，换板子都治不好软件设置的问题。

::: info 核心概念
- **单元状态指示灯（Unit Status LED）**：每台单元前面板同一位置的状态 LED，用颜色与闪烁频率编码单元当前状态，是整套诊断树的入口
- **菊花链吞吐量（Daisy-chain Throughput）**：每条菊花链支持最高 1.7 MSa/s 的总数据率，REC 单元四条链累计上限 7.8 MSa/s，超限时 REC 灯呈正常频率闪烁的红色
- **APIPA（Automatic Private IP Addressing，自动私有 IP 寻址）**：DHCP 服务器不可用时操作系统自动分配 169.254.x.x 段地址的机制，是 REC 单元「连不上却没坏」时最后的访问通道，地址印在机身标签上
- **WS-Discovery / LLMNR / SSDP**：Windows 在「网络」里发现第三方设备的三种协议，公司安全策略常将其禁用，是「设备在线却看不见」的头号网络原因
:::

## 二、LED 灯语：颜色与频率的编码表

所有单元的指示灯遵循同一套编码规则：**颜色定性质，频率定状态**。闪烁类型由一个约 2 秒的定时循环定义：固体（稳态）全程点亮，「正常」频率按固定节奏闪，「快」（等待中）频率约翻倍，「慢」（睡眠）频率减半：

![闪烁定时循环：固体/正常/快/慢四种闪烁类型的时序定义](/images/rs-troubleshooting/fig1-blink-cycle.png)
*（图源：网络 侵删）*

各单元通用状态里，最需要条件反射式记住的是四条：**白色/正常=正在启动初始化**（别急着断电）、**青色/正常=固件升级中**（此时断电风险最高）、**品红/快闪=被 GUI 里的识别功能点名**（默认 5 秒，用于多台设备同场时认机，时长可编辑）、**固体红色=内部错误**（这是真故障，重启无效再联系支持）。

UPS 单元值得单独讲，因为它管电，分诊里属于「先保命」的科室。它有三颗灯：状态灯（绿=正常）、电源灯（描述直流输入与充电状态）、BAT 灯（外部电池单元）。电源灯的语义按优先级排：**固体绿=直流供电且电池满**，**正常频率绿=直流供电充电中**，**固体黄=电池放电中**（设备靠电池活，要开始算剩余时间了），**正常频率黄=放电且电量低**（准备安全收尾），**固体青=有直流却不充电**。这一条最容易被误读成故障，实际是高负载、过热或电池异常触发的保护，负载降回 75 W 以下自动恢复充电；**快闪红=过载/过热/电量过低/一般错误**，属于必须立即干预的级别。

![UPS 单元状态指示灯的语义表](/images/rs-troubleshooting/fig4-ups-status.png)
*（图源：网络 侵删）*

![UPS 电源指示灯：从固体绿到快闪红的优先级序列](/images/rs-troubleshooting/fig5-ups-power.png)
*（图源：网络 侵删）*

REC 单元的状态灯直接对应录制流程：正常频率绿=发布数据未录制，固体绿=录制中，快闪绿=等待触发，慢闪绿=等待唤醒，快闪黄=正忙（停录/关文件/同步，此时别拔电），快闪红=**存储几乎满**，正常频率红=**菊花链超吞吐量**。注意这两条红色是 REC 特有的「科室」，指向存储与吞吐，而不是内部错误。

![REC 单元状态指示灯：录制流程与两种红色告警](/images/rs-troubleshooting/fig6-rec-led.png)
*（图源：网络 侵删）*

调节单元与 DI 单元在传输数据时亮固体绿/青（青色表示叠加了分路/平衡/校准等活动状态），通道电源过载时快闪红且**保持到用户操作为止**。这类「锁存型」告警是故意设计的：瞬时过载转瞬即逝，锁存让你来得及看清是哪个通道。ECAT 单元（EtherCAT 从设备）有两套灯：试验指示灯按 Off/闪烁/单闪/On 描述初始化到运行的四个从站状态，错误灯按单闪/双闪/常亮区分本地错误/看门狗超时/应用程序控制器故障。

## 三、症状分型：把第 16 章的表读成一棵树

理解灯语之后，第 16 章的三列表就可以重新组织。原表按「错误条件」罗列约二十条，本文按**分诊科室**归成四类，每类给出发病的典型机理：

### 电源科：UPS 红色闪烁与无法关机

UPS 指示灯红闪的第一梯队原因按检查成本排序：主电源丢失（查断路器，是不是整个插座排都没电）、直流电源（适配器插头、输出电压）、电源线与布线（有没有被座椅压断、接插件松脱）。第二梯队才是设备本身：电源缓冲器（电池）缺陷、电量太弱、或只充了部分电。另一条容易被忽略的条目：**UPS 无法断电**。按开/关按钮 10 秒以上是手册给的复位手段，机理是微处理器在通信中断后卡在等待状态，长按强制走关机流程。

### 网络科一：看得见连得上（浏览器层）

升级固件后 Web 应用行为怪异、数据显示不对？先别怀疑设备：**浏览器缓存仍留着旧版页面**。Windows 按 Ctrl+F5、Mac 按 Command+R、Linux 按 F5 强制刷新，这是第 16 章排位最前的条目之一，因为命中率极高。Web 应用打不开的另一个高频原因是**超过支持的最大客户端数**：REC 的 Wi-Fi 接入点最多 4 个客户端，之前的手机没断开占着名额，关闭不用的客户端或等待其掉线即可。

### 网络科二：设备在线却看不见（发现层）

这是最考验耐心的一类。REC 在 Windows 资源管理器「网络」里不显示、录制文件无法访问，原因层层嵌套：PC 的 Windows 版本太老（早于 Windows 7 不支持）、WS-Discovery 未启用（Windows 搜索框输 services 打开服务管理器开启）、REC 内的 Samba 服务器被禁用（重启 REC 单元）、**公司网络策略整体禁用了 LLMNR/WS-Discovery/SSDP/NBNS**（只能联系 IT 为 REC 主机名加 DNS 记录，或改用 SFTP 连接）。发现过程本身也需要耐心：Windows 发现新单元最长要 20 秒，且 Windows 10 默认可能禁用 SSDP 发现服务。

![第 16 章故障排除表（上）：电源、浏览器缓存、网络发现类条目](/images/rs-troubleshooting/fig2-trouble-table1.png)
*（图源：网络 侵删）*

### 网络科三：IP 配置错位（地址层）

静态 IP 设到主机网段之外、主机子网掩码/网关与单元静态 IP 不匹配、忘了静态 IP 是多少。三种情况的共同病根是「两端的地址参数没有对上账」。手册给的出路有两条：通过 Wi-Fi 接口进去改（静态 IP 设置在主机 IP 范围之外时，Wi-Fi 接口仍可能可达），或改主机 IP 范围；忘了地址则把单元接到有活动 DHCP 服务器的网络重新获取，或**重置为出厂默认设置**（IP 设置会恢复默认值）。注意恢复出厂的手段是长按 REC 的「模式」按钮 15 秒。这是一招「核选项」，会清掉全部配置；多台设备同场时还要防名称冲突：两台 REC 默认 SSID 只差序列号，重命名设备或 SSID 防连错。

![第 16 章故障排除表（下）：IP 配置、Samba、SFTP 与名称冲突](/images/rs-troubleshooting/fig3-trouble-table2.png)
*（图源：网络 侵删）*

### 存储与传输科：Windows 访问断断续续与吞吐超限

用资源管理器访问 REC 内部存储时断时续，第 16 章点名的元凶是**网络上的主动安全产品**：病毒扫描、行为扫描、恶意设备检测会干扰 REC 与网络的连接，解法是联系 IT 给设备加白。而 REC 灯「正常频率红色」指向的吞吐超限，本质是一道算术题。

这个公式回答的问题是：一条菊花链还能再塞多少通道？每链总吞吐上限 1.7 MSa/s，把链上所有通道的采样率加起来与它比较，超了就只有两条路：降采样率，或把通道分到其他链。REC 整机累计上限 7.8 MSa/s，四条链同时规划时要再对一次总账。

$$\sum_{i \in \mathrm{chain}} f_{s,i} \le 1.7\ \mathrm{MSa/s}, \qquad \sum_{\mathrm{all\ chains}} f_{s,i} \le 7.8\ \mathrm{MSa/s}$$

举一组具体数字：一条链挂 20 个通道、每通道 51.2 kHz，合计 1.024 MSa/s，余量充足；为看高频把其中 10 个通道提到 102.4 kHz，总账变成 1.024+0.512=1.536 MSa/s，逼近上限；再有一个通道升级带宽，就随时可能把整条链推过 1.7。这种「配置膨胀」式的超限几乎不会在单通道调试时暴露，只在全通道齐跑时发作，与 REC 灯红闪的时间点（正式采集开始后）完全吻合。

## 四、numpy 分诊器：把灯语写成代码

读表是入门，把判定逻辑写成代码才算真正内化。下面这段自包含代码把 REC 与 UPS 的灯语表存成字典，输入观测到的（颜色，频率）组合，输出分诊结论与下一步动作，逻辑与上文状态表一一对应，可直接运行：

```python
import numpy as np

# REC 灯语表：(颜色, 频率) -> (状态, 分诊科室, 动作)
REC_LED = {
    ('绿', '正常'): ('发布数据未录制', '正常',   '可开始录制'),
    ('绿', '固体'): ('录制中',         '正常',   '勿断电, 结束后安全停录'),
    ('绿', '快'):   ('等待触发',       '正常',   '检查触发条件'),
    ('绿', '慢'):   ('等待唤醒',       '正常',   'Web 应用或按钮唤醒'),
    ('黄', '快'):   ('忙: 停录/关文件/同步', '保护', '等待完成, 勿拔电'),
    ('红', '快'):   ('存储几乎满',     '存储科', '清理 SSD 或导出后删除'),
    ('红', '正常'): ('菊花链超吞吐',   '吞吐科', '核对每链 1.7 MSa/s 上限'),
}
UPS_POWER = {
    ('绿', '固体'): ('直流供电, 电池满',   '正常',   ''),
    ('绿', '正常'): ('直流供电, 充电中',   '正常',   ''),
    ('黄', '固体'): ('电池放电中',         '电源科', '算剩余时间, 准备收尾'),
    ('黄', '正常'): ('放电且电量低',       '电源科', '尽快安全停机保存数据'),
    ('青', '固体'): ('有直流但停充(保护)', '电源科', '查过载/过热, 降载自愈'),
    ('红', '快'):   ('过载/过热/电量过低', '电源科', '立即查断路器/电源/布线'),
}

def triage(table, color, rate):
    return table.get((color, rate),
                     ('未知组合', '查手册', '先复核观测: 颜色与频率各是什么'))

print(triage(REC_LED,   '红', '快'))     # 存储科
print(triage(REC_LED,   '红', '正常'))   # 吞吐科
print(triage(UPS_POWER, '青', '固体'))   # 电源科: 停充保护

# 吞吐分诊: 通道采样率清单 (kHz) 对每链 1.7 MSa/s 上限
chans = np.array([102.4]*10 + [51.2]*10)    # 10 个高频 + 10 个常规
load = chans.sum() / 1000                    # 换算 MSa/s
print('链吞吐 %.3f MSa/s, 余量 %.3f -> %s' % (load, 1.7-load,
      'OK' if 1.7-load > 0.1 else '贴线, 加通道/升采样前先算账'))
```

四个输出的看点：`('红','快')` 与 `('红','正常')` 这对最容易混淆的症状被正确分流到存储科与吞吐科：前者动作是清理 SSD，后者动作是核对采样率账本；`('青','固体')` 被识别为「停充保护」而非故障，动作是降载等待自愈而不是报修；吞吐分诊给出量化余量 0.164 MSa/s，把「红闪了再说」变成「配置阶段就留余量」。灯语表的正确用法从来不是背，而是**把判定树固化成不需要现场思考的形式**：打印成卡片贴在设备箱里，是这段代码最好的归宿。

## 五、防患于未然：三件比排障更省时间的事

诊断树的最高境界是少用。三件事能显著降低故障发生率与排障时间：

**其一，装机时就把「可发现性」打通**。PC 网卡设「自动获取 IP 地址」（Windows 默认），确认 SSDP 服务已启用，用机身标签上的 APIPA 地址做一次点对点连通性验证并抄进项目档案：这条后备通道在公司网彻底封死发现协议时是唯一的门。同时验证 Wi-Fi 接入点模式：默认 SSID 为 SCADAS-RS-2.4/5.0-加序列号、最多 4 客户端；多台 REC 同场第一件事是重命名设备或 SSID、改密码（8 字符以上含大写与特殊字符），防连错设备。

**其二，把吞吐与存储的账算在配置阶段**。每链 1.7 MSa/s、整机 7.8 MSa/s 的上限在规划通道清单时就要过一遍（上文代码最后一行就是为此），而不是等 REC 红闪再回头查。存储同理：按总数据率乘计划录制时长估算 SSD 占用，长时录制配「定时分段+到站搬运」策略，别把「存储几乎满」的红色留给路试高峰期。

**其三，固件升级走完正确闭环**。升级中灯呈青色正常闪烁，这一阶段断电是所有操作里后果最重的一条；升级完成后第一次打开 Web 应用务必强制刷新（Ctrl+F5），把「行为怪异」这个最高频的「假故障」直接消灭在浏览器缓存里。

## 一句话记住

LED 是分诊台不是显示器：颜色定性质、频率定状态；快闪红 REC 查存储、正常频率红查每链 1.7 MSa/s 吞吐账、UPS 固体青是停充保护等自愈；连不上先 Ctrl+F5 再查 SSDP/WS-Discovery，最后靠机身 APIPA 地址进场。
